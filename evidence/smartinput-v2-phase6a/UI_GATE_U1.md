# UI Gate U1 — 미매칭 검수 배치 제안

- 작업 ID: `NEXUS-SI-V2-06A`
- Gate 상태: **제안만 작성됨 / 사용자 미승인 / 제품 UI 구현 금지 유지**
- 기준: 기존 화면과 저장 흐름, DOM, 버튼, 열, 탭, 단축키, 저장 클릭 수를 바꾸지 않은 상태에서 다음 구현 단계의 선택지만 비교한다.
- 데이터 경계: 어느 안을 선택해도 화면은 `ONEAPP_ORDERQ_UNRESOLVED_REVIEW_READ_ADAPTER_V1`만 호출한다. `orderops`, SmartInput 또는 다른 앱이 ORDER Q IndexedDB나 Store를 직접 열어서는 안 된다.

## 공통으로 보여야 하는 내용

세 안 모두 같은 Read Model을 사용한다. 목록에는 확정 당시 원본 상품코드·상품명·규격·단위, 창고, `businessDate`, 입력수량, 구매/판매 부호수량, `미반영` 상태와 미반영 부호수량을 표시한다. 공식재고 값은 `null`로 유지하고 0으로 표시하지 않는다. 원 전표 종류·문서 ID·행 ID·문서 Revision·Revision ID와 전표 추적 링크, 링크 무결성 상태도 확인할 수 있어야 한다.

후보는 현재 Product Snapshot의 검수 참고다. 회사 범위의 정확한 원문 상품코드가 한 건일 때만 정확 후보로 표시하고, 이름 후보는 별도 참고로 둔다. 모든 후보 옆에는 `자동확정 아님`을 명시한다. 재매칭 대상을 선택한 뒤에는 실행 전에 영향 전표·행·수량 합계·창고·발생일·최신 실사 checkpoint와 `정상 적용 가능`/`실사 판단 필요`를 보여 주되, 이 Gate 승인만으로 실제 재매칭 버튼이나 쓰기를 추가하지 않는다.

## A안 — 기존 재고·출고 결과 영역 재사용

변경 위치는 `orderops/list.html`의 기존 `창고재고` 결과 화면이 사용하는 `#resultsPanel`, `#previewTable`, 현재 검색·정렬·필터 영역이다. 기존 결과 영역 안에서 미매칭 검수 자료를 전환해 보여 주고, 상세 추적과 영향 미리보기도 같은 결과 영역을 교체해 사용한다. 새 전역 패널이나 별도 팝업은 만들지 않는다. 실제 구현 시에는 기존 필터 메뉴에 검수 상태 한 항목을 추가하거나, 기존 창고재고 행의 상태 진입을 재사용하는 두 방식 중 하나를 상세 설계해야 한다.

사용자는 이미 출고·창고재고 화면에 있다면 기존 화면 선택 뒤 검수 상태 선택 1회가 추가되고, 특정 항목의 전표 링크 또는 영향 상세를 볼 때 1회가 더 필요하다. 목록의 핵심 필드는 기존 결과 표의 상품·창고·수량·상태 자리를 재사용하고, 문서/행/Revision과 checkpoint 근거는 같은 영역의 상세 상태로 전환한다.

장점은 현행 출고·재고 업무 맥락을 유지하고 새 상위 탐색 구조를 만들지 않으며, 롤백이 해당 결과 렌더러와 Adapter 연결 제거로 국한된다는 점이다. 단점은 `orderops`와 `orderq-vnext`가 서로 다른 앱·저장소 계약을 가진 현재 구조에서 새 Read Adapter 소비 관계를 명시해야 하고, 기존 업로드 기반 창고재고와 공식 미반영 자료를 시각적으로 혼동하지 않도록 상태 문구를 강하게 분리해야 한다는 점이다.

모바일에서는 현재 결과 표의 가로 스크롤 규칙을 그대로 쓰되 긴 문서 ID와 Revision은 상세 상태에서 줄바꿈해야 한다. 다크 모드는 기존 결과 표 토큰을 재사용하므로 영향이 가장 작지만, `미반영`, `REVIEW_REQUIRED`, `DECISION_REQUIRED`의 대비를 별도로 검증해야 한다. 예상 구현 공수는 계약 연결·상태 전환·반응형/다크/회귀를 포함해 약 2~3 개발일이다. 롤백은 소비 등록과 결과 영역의 검수 분기만 되돌리며 ORDER Q 데이터는 삭제하거나 변환하지 않는다.

## B안 — 기존 팝업 안에서 검수

변경 후보는 SmartInput 단계 5의 기존 실사 checkpoint 결정 팝업이다. 미매칭 목록에서 항목을 고른 뒤 같은 팝업 골격에 원문 상품정보, 후보, 영향 전표와 checkpoint를 순차 표시하는 방식이다. 새 팝업을 만들지는 않지만 팝업의 역할을 “전표 저장 중 실사 결정”에서 “사전 미매칭 검수”까지 넓히게 된다.

사용자는 검수 진입 1회, 후보 선택 1회, 영향 확인 1회로 보통 2~3회의 추가 클릭이 필요하다. 좁은 팝업 안에서 공통 필드 전부를 한 번에 보이기 어려워 요약과 전표 링크 상세를 순차 단계로 나눠야 한다.

장점은 단계 5에서 이미 검증한 포커스 복원, 취소, 모바일·다크 팝업 골격과 checkpoint 문구를 재사용할 수 있다는 점이다. 단점은 현재 팝업이 SmartInput의 “저장 전 일시적 결정”에만 존재하므로 ORDER Q의 지속적인 검수 목록과 발견성이 맞지 않고, 활성 SmartInput 작업본·저장 흐름에 새로운 진입 경로를 결합할 위험이 크다는 점이다. 화면이 좁은 모바일에서 다단계 이동이 늘고, 다크 모드 자체는 기존 토큰을 쓸 수 있어도 긴 추적 정보와 후보 목록의 스크롤·포커스 회귀가 커진다.

예상 구현 공수는 팝업 상태기계 분리와 작업본 보호 회귀를 포함해 약 3~4 개발일이다. 롤백은 새 검수 모드와 호출부만 제거하고 기존 단계 5 팝업을 원래 저장 전 용도로 유지한다. 팝업 의미 확장 때문에 A안보다 rollback 검증 범위가 넓다.

## C안 — 신규 표 열·탭·버튼·패널

변경 위치는 ORDER Q 또는 출고 화면의 새 `미매칭 검수` 탭/버튼과 전용 목록·영향 패널이다. 새 표 열에는 공식재고 상태, 미반영 수량, 링크 수, 무결성, 후보 상태, 실사 판단을 배치하고 별도 상세 패널에서 전표 링크와 checkpoint를 펼친다.

전용 진입 버튼 1회와 항목/상세 선택 1~2회가 추가된다. 정보 밀도와 발견성은 가장 좋고 대량 검수, 페이지 이동, 상태 필터를 명확하게 설계할 수 있다. 반면 신규 DOM, 열, 탭, 버튼, 패널, 단축키 충돌 검토, 접근성, 빈/오류/로딩 상태, 모바일 재배치와 다크 테마를 모두 새로 검증해야 한다. 영구 검수 UI와 재매칭 실행 배치로 범위가 번지기 쉬워 이번 단계의 최소 변경 원칙과 가장 거리가 멀다.

예상 구현 공수는 약 4~6 개발일 이상이다. 롤백은 새 탐색 요소·표·패널·라우팅과 소비 등록을 함께 제거해야 하며, 사용자 북마크나 저장된 표 설정이 생기면 호환 정리까지 필요하다. 데이터 삭제나 DB migration은 어느 경우에도 rollback에 포함하지 않는다.

## 권장안과 승인 경계

**권장안은 A안, 기존 재고·출고 결과 영역 재사용이다.** 새 상위 UI 구조를 만들지 않고 현재 업무 맥락과 결과 영역을 유지하며, Adapter 소비와 한정된 렌더링 분기만 후속 구현 범위로 묶을 수 있어 변경량과 rollback이 가장 작다. 다만 `orderops`가 `orderq-vnext`의 새 Read Adapter 소비자로 등록되는 점과 공식 `미반영`을 업로드 재고 0과 혼동하지 않는 표시를 사용자 승인 시 명시적으로 확정해야 한다.

이 문서는 구현 승인이 아니다. 사용자가 A/B/C 중 하나와 세부 진입 방식을 승인하기 전에는 제품 HTML/CSS/JS, 표 열, 필터, 버튼, 탭, 패널, 팝업, 레이아웃, 단축키 또는 저장 클릭 수를 변경하지 않는다. 단계 6B의 재매칭 command와 재고 반영도 별도 승인·작업이다.
