## 1. 목적

이미 완료된 출고관리 3개 섹션과 좌측 주문 요약을 유지하면서 다음 잔여 문제만 해결한다.

1. 주문만 조회한 뒤 재고를 추가해도 중앙 기본 6열과 사용자 표 설정을 유지한다.
2. 좌측 4열 표를 유지하면서 선택 거래처 담당 변경 경로를 복원한다.
3. ERP 주문의 `창고코드`를 조회용 창고로 정확히 인식하고, `창고`와 충돌하면 관리자가 사용할 원본 열을 선택한다.
4. 담당자별 주문 건수를 현재 창고·지역 조회 범위에 맞게 계산한다.
5. 재고 단독 조회에서 원본 창고별 수량과 재고 합계를 함께 표시한다.
6. 주문단위 또는 재고단위가 공란이면 비교 근거 없이 잔량을 계산하지 않는다.
7. 앱헤더에 몰린 저장·출력·복구 조작을 중앙 하단 작업바로 분산한다.
8. 파일 불러오기와 분석 실행을 앱헤더에서 시작할 수 있게 한다.
9. 검색 결과 0건과 원본·필터 상태를 구분해 표시한다.
10. `System.IO` 콘솔 표현을 제거하고 실제 업무 상태 표시로 통합한다.
11. 표 설정 조작을 한 메뉴로 묶되 기존 저장값과 동작을 유지한다.
12. 390px 모바일에서 좌측·중앙 접근과 우측 재열기를 보장하는 별도 배치를 제공한다.

문서 작성은 생산 소스 변경이나 배포 승인이 아니다. 사용자가 이 명세의 개발을 지시하면 구현부터 PR, 병합, Pages 배포와 운영 기술검증까지 한 범위로 수행한다.

적용 순서는 다음과 같다.

1. 사용자의 확정 요구와 본 명세

## 3. 완료 기준선과 변경 금지 범위

다음 항목은 PR #575에서 완료됐으므로 재구축하거나 이전 방식으로 되돌리지 않는다.

- 앱헤더 아래 동일 부모의 좌측·중앙·우측 3개 섹션
- 좌측 상시 표시와 좌우 독립 폭 조절
- 우측 닫기·재열기·너비·열림 상태 보존
- 우측을 사용자가 다시 연 뒤 화면 갱신만으로 닫지 않는 동작
- 좌측 필터 순서 `창고 → 담당 → 지역`
- 좌측 표의 `거래처 · 수량 · 금액 · 적요` 4개 열
- 담당자 건수 버튼의 선택·재선택 해제와 `aria-pressed`
- 주문서가 있으면 재고·분석 전에도 중앙 기본 분석표를 표시하는 진입 경로
- 주문·재고·구매·판매 단독 자료를 여는 읽기 전용 보기 경로
- 분석 전 편집·ORDER Q snapshot·fingerprint 복구와 정상 분석본 보호
- 분석 뒤 `주문 상세 F5`를 별도 보기로 유지하는 구조
- 명시적으로 서로 다른 주문단위의 무근거 합산·배정·잔량·구매필요 차단
- 1024px·125% 상당 폭의 패널 조절과 우측 키보드 재열기
- 직원 적요 `note1Original/note1`과 일반 적요 `noteOriginal/note` 분리
- 기존 부분출고·대체·보류·취소·충돌·출력 계약

위 진입 경로가 존재하더라도 다음 결함은 완료로 보지 않는다.

- 주문만 불러온 뒤 재고를 추가하면 중앙 기본표가 6열이 아니라 15열로 확장되는 문제
- 재고 단독 조회에서 합계만 보이고 원본 창고별 수량 열이 사라지는 문제
- 재고단위 공란을 비교 가능으로 처리하는 문제

담당자 변경은 중앙 선택 열·`주문 상세`와 좌측의 선택 거래처 변경 조작을 모두 제공한다. 두 경로는 같은 변경 함수를 사용하며 별도 저장 계약을 만들지 않는다.

## 5. 화면 배치 명세

### 5.1 앱헤더

앱헤더는 56px 단일 행, 배경 `#0b1021`, 좌측 24px 시작선과 `출고관리` 명칭을 유지한다. 로고·버전 배지를 다시 추가하지 않는다.

앱헤더의 주요 조작 순서는 다음과 같다.

1. `통합 불러오기`
2. `주문서 불러오기`
3. `창고재고 불러오기`
4. `출고분석 Enter`
5. `더보기`
6. `환경설정`

`주문서 불러오기`는 하나의 진입 조작에서 다음 기존 경로를 구분해 제공한다.

- 주문 Excel 선택
- ORDER Q 저장 주문 선택 영역 열기·포커스

`더보기`에는 다음 저빈도 조작을 배치한다.

- 구매 참고자료 불러오기
- 판매 참고자료 불러오기
- 현재 자료 새로고침
- 클라우드 완료본 불러오기

기존 input과 handler를 재사용한다. 화면 이동 과정에서 동일 `id`를 가진 복제 버튼이나 두 번째 실행 handler를 만들지 않는다. 파일 input은 기존 `integratedInput`, `ordersInput`, `inventoryInput`, `purchasesInput`, `salesInput`을 유지한다.

### 5.2 중앙 표 상단

중앙 상단에는 현재 표를 찾고 보는 조작만 둔다.

1. 고정 표시 `검색`
2. 검색 입력 F3
3. `검색 해제`
4. 보기 전환
5. `필터초기화 F2`
6. `표 설정`
7. 우측 패널이 닫힌 경우 `우측 열기`

재고부족·미매칭·규격·창고·담당 조회는 보기 전환 또는 표 설정과 연결된 기존 경로에서 계속 접근할 수 있어야 한다. 우측 재열기 버튼은 가로 스크롤되는 도구 묶음 밖에 둔다.

### 5.3 중앙 하단 고정 작업바

중앙 작업표와 같은 작업영역 안에 다음 순서로 배치한다.

1. `스마트입력 F4`
2. `저장 F8`
3. `화면인쇄 F9`
4. `Excel 출력 F10`
5. `이전복구`

하단 작업바는 viewport가 아니라 중앙 작업영역을 기준으로 고정한다. 다음 조건을 지킨다.

- 좌측·우측 패널 위를 덮지 않는다.
- 표 마지막 행과 가로 스크롤바를 덮지 않는다.
- 표의 세로·가로 스크롤과 분리된다.
- 1024px·125%에서도 모든 주요 조작에 키보드로 접근할 수 있다.
- 좁은 폭에서 줄바꿈으로 두 줄이 되지 않으며, 필요하면 작업바 자체를 가로 스크롤한다.
- 인쇄할 때 작업바를 출력하지 않는다.

기존 `smartInputButton`, `headerCloudSaveButton`, `printButton`, `downloadButton`, `headerRestoreButton` 기능과 단축키를 재사용한다. DOM을 이동하거나 기존 ID를 보존한 새 위치에서 한 번만 렌더한다.

### 5.4 좌측 선택 거래처 담당 변경

좌측 4열 표 아래에 `선택 거래처 담당 변경` 영역을 둔다.

- 주문서 행을 선택하기 전에는 담당 입력과 적용 버튼을 비활성화한다.
- 선택 후 현재 담당, 적용 대상 거래처와 예상 변경 행 수를 표시한다.
- 담당자는 기존 목록 검색·선택과 새 이름 직접 입력을 모두 허용한다.
- 적용은 중앙 담당 편집과 동일한 `setCustomerManager()` 계열 함수를 사용한다.
- 상단 `담당` 조회 select를 배정 변경 입력으로 겸용하지 않는다.
- 적용 뒤 현재 창고·담당·지역 조회, 선택, 좌측·중앙 스크롤과 미저장 입력을 보존한다.
- 현재 담당 조회에서 행이 벗어나면 필터를 임의 해제하지 않고 조회 0건 또는 다음 행 접근 상태를 표시한다.

적용 범위는 기존 계약을 따른다.

- 안정 거래처 ID·코드가 있으면 현재 작업공간의 같은 거래처 키 전체 주문행
- 안정 ID·코드가 없으면 현재 주문·창고 배송 단위
- 상호명만 같은 다른 거래처는 변경하지 않음
- 필터로 숨은 대상도 같은 안정 거래처 키면 포함
- 변경 성공 후 중앙·담당 건수·변경 이력·임시저장 상태 갱신
- 저장 실패 또는 변경 함수 오류 시 완료 표시 금지와 화면 입력 보존

### 5.5 중간 폭·모바일 패널 배치

좌측 최소 220px와 우측 최소 180px에 중앙 표를 더한 세 섹션을 390px의 한 행에 강제로 넣지 않는다. 세 섹션은 앱헤더 아래 같은 부모와 좌측→중앙→우측 DOM 순서를 유지하면서 다음처럼 재배치한다.

| 가용 CSS 폭 | 출고관리 배치 |
|---|---|
| 1100px 이상 | 좌측·중앙·우측 같은 행, 좌우 독립 resize |
| 640~1099px | 좌측+가용 폭 중앙 같은 행, 좌측 너비 조절 유지, 우측 너비 조절형 overlay sheet |
| 639px 이하 | 좌측 전체 폭 상단+중앙 전체 폭 하단, 우측 overlay sheet |

- 390px에서 좌측은 숨기지 않고 최대 `38dvh`의 자체 스크롤 영역으로 둔다. 중앙은 남은 작업 높이를 사용하고 표 내부에서 가로·세로 스크롤한다.
- 640~1099px의 좌측은 최소 220px, 중앙은 최소 320px을 보장하는 가용 범위에서 resize한다. 우측 overlay는 최소 180px에서 `min(420px, calc(100% - 16px))`까지 독립 resize한다.
- 639px 이하에서는 좌우 resize handle을 비활성화하고 우측 overlay 폭을 `min(320px, calc(100% - 16px))`로 제한한다.
- breakpoint 전환은 저장된 데스크톱 좌우 너비를 덮어쓰지 않으며 넓은 화면 복귀 시 이전 폭을 복원한다.
- breakpoint 왕복과 화면 갱신 뒤에도 우측 열림 상태, 패널 내부 입력·선택·스크롤을 보존한다.
- `주문 목록`, `분석표`, `우측 열기` 바로가기를 제공하며 키보드 포커스와 터치 조작을 모두 지원한다.

## 6. 표 설정 메뉴

### 6.1 중앙 기본표 열 key 안정화

`readiness` 보기의 고정 업무 열은 위치 index가 아닌 업무 role을 영구 key로 사용한다.

```text
shipping:readiness:customer
shipping:readiness:productName
shipping:readiness:orderQuantity
shipping:readiness:deliveryNotice
shipping:readiness:stockQuantity
shipping:readiness:calculatedQuantity
shipping:readiness:productAggregateQuantity
shipping:readiness:orderUnit
shipping:readiness:inventoryUnit
shipping:readiness:comparisonStatus
shipping:readiness:productCode
shipping:readiness:specification
shipping:readiness:manager
shipping:readiness:warehouse
shipping:readiness:note
```

재고 유무로 `재고·잔량` 두 열이 삽입되거나 제거돼도 다른 열 key는 변하지 않아야 한다. 기본 가시 열은 다음과 같다.

- 주문만: `거래처 · 상품 · 주문수량 · 직원 적요`
- 주문+재고: 위 4열 + `재고 · 잔량`

나머지 9개 보조 열은 사용자가 명시적으로 표시하지 않은 한 숨김을 유지한다. 분석 실행도 기본 보기나 열 가시성을 강제로 바꾸지 않는다.

기존 위치 기반 key는 호환 이전한다. 현재 주문만·주문+재고 두 배열의 index와 header를 role로 대조해 다음 저장 상태를 한 번 변환한다.

- 열 숨김
- 열폭
- 열 순서
- 열 정렬
- 열 조건
- 저장 화면 양식의 `columnWidths`, `columnOrder`, `hiddenColumns`, `sortSetting`, `columnFilters`

호환 이전은 인식한 key만 변환하고 알 수 없는 key를 다른 열에 추정 적용하지 않는다. 사용자 설정이 없는 최초 진입과 이전 뒤 유효 설정이 없는 경우에만 기본 숨김을 적용한다. 이전 완료를 업무 workspace나 Cloud plan에 기록하지 않는다.

연속 입력 완료조건은 다음과 같다.

1. 주문만 읽으면 4열이다.
2. 같은 세션에서 재고를 추가하면 6열이다.
3. 출고분석 뒤에도 6열이다.
4. 중간 재접속·복구 없이 위 상태를 유지한다.
5. 사용자가 이미 표시한 보조 열과 저장 폭은 재고 추가 뒤에도 유지한다.

### 6.2 통합 표 설정 메뉴

중앙 상단의 `표 설정` 버튼은 다음 기존 조작을 하나의 접근 가능한 메뉴로 제공한다.

- 열 표시
- 열폭 저장
- 열폭 초기화
- 화면 양식 선택
- 화면 양식 저장
- 기본 양식 지정
- 화면 양식 삭제
- 창고 보기·배색
- 담당자 보기·배색

다음 계약은 변경하지 않는다.

- 저장키 `oneapp.shipping.table-widths.v1`
- 저장키 `oneapp.orderops.order-view-presets.v1`
- 기존 창고·담당 배색 저장키와 값
- 탭별 열 표시·순서·필터·정렬·열폭
- 흰색 배색 취소와 파스텔·원색 선택
- 양식 적용 시 업무 데이터·편집값·복구 데이터·Cloud plan 불변

메뉴는 버튼의 `aria-expanded`, 메뉴 이름, Tab 이동, Enter/Space 실행, Escape 닫기, 바깥 클릭 닫기를 지원한다. 메뉴를 닫아도 검색·필터·선택·입력·표 스크롤은 바뀌지 않는다.

## 7. 창고코드 매핑

### 7.1 기본 별칭

`ORDER_CANONICAL_ALIASES["창고"]`에 `창고코드`를 additive alias로 추가한다.

```js
"창고": Object.freeze(["창고", "출고창고", "창고코드"])
```

문자값은 표시용 원본 의미를 유지한다. `88`, `01`, `003` 같은 코드를 숫자로 변환하거나 선행 0을 제거하지 않는다.

### 7.2 우선순위와 충돌

- 관리자 저장 매핑이 있으면 기존 저장 매핑을 우선한다.
- 원본에 후보가 하나면 해당 열을 표준 창고로 사용한다.
- `창고`와 `창고코드` 등 후보가 둘 이상이고 선택된 열이 명확하지 않으면 조용히 한쪽을 덮어쓰지 않는다.
- 서로 다른 값의 복수 후보는 기존 별칭 등록만으로 해결하지 않고 전용 `창고 원본 열 선택` 단계로 보낸다.
- 충돌은 해당 파일의 창고 조회를 `미지정` 성공으로 위장하지 않는다.
- 주문창고 `88`을 재고의 `1창고`, `3서울` 등에 자동 연결하지 않는다.

권장 오류 코드는 `ORDER_WAREHOUSE_COLUMN_CONFLICT`다. 기존 외부 오류 코드 계약이 있으면 호환 코드를 유지하고 UI 의미만 통일한다.

충돌 해결 화면과 재검증 계약은 다음과 같다.

1. 후보별 원본 header, 비공란 값 수, 고유값 예시와 충돌 행의 `창고`·`창고코드` 값을 나란히 표시한다.
2. 관리자가 `이번 주문 파일의 창고로 사용할 열` 하나를 선택한다. 첫 번째 열이나 별칭 순서로 자동 선택하지 않는다.
3. 선택 뒤 원본 source matrix를 다시 파싱하고 창고 필터, 담당자별 주문 건수, 주문 건수, 오류 건수를 다시 계산한다.
4. 재검증 성공 전에는 파일 적용·분석·완료로 표시하지 않는다. 실패하면 선택 화면과 원본 입력을 유지한다.
5. 선택값은 현재 workspace와 기존 복구 record에 `sourceHeaderSignature`, 주문 import 종류, 선택한 원본 header를 함께 저장한다.
6. 기존 매핑 저장을 관리자가 명시한 경우에만 같은 header signature·같은 import 종류의 다음 파일에 재사용한다. 다른 파일 구조와 후보 구성이면 다시 선택한다.
7. 선택 변경은 기존 파생 분석본을 `재분석 필요`로 표시하지만 원본 파일·두 열 값·source fingerprint·공식 완료본·출고결과를 덮어쓰거나 삭제하지 않는다.

### 7.3 재고 단독 조회 열

주문 없이 재고만 읽은 `창고재고 · 읽기용` 표는 다음 열을 원본 순서로 표시한다.

1. 상품코드
2. 상품
3. 규격
4. 단위
5. 파서가 `warehouseQuantity`로 정상 판정한 모든 창고별 수량 열
6. 재고 합계

`1창고`, `2전송`, `3서울`, `4전송`, `7진영`처럼 실제로 인식된 창고 열만 포함한다. `기본`, `전송`, `창고`, 구매가·단가·가격·금액·원가 역할의 열은 창고 수량으로 표시하거나 합산하지 않는다.

값은 `sourceFiles.inventory.columns`의 `sourceIndex`와 검산된 source matrix를 사용해 재구성할 수 있다. 별도 가짜 주문이나 inventory shadow를 만들지 않는다. 공란·0·음수·소수·선행 0 상품코드는 원본 의미를 유지하며, 재고 합계는 기존 signed sum 검산값을 표시한다.

재고 단독 표에는 주문수량·잔량·구매필요를 만들지 않는다. 재접속·이전복구 뒤에도 같은 동적 창고 열과 원본 순서를 복원한다.

### 7.4 재고단위 공란 처리

상품별 재고 비교는 다음 조건을 모두 만족할 때만 `quantityComparable=true`로 판정한다.

1. 주문단위가 정확히 하나이고 공란이 아님
2. 재고단위가 공란이 아님
3. 정규화한 주문단위와 재고단위가 일치
4. 별도의 승인된 단위 변환이 필요하지 않음

재고단위가 공란이면 주문단위가 `EA`로 명시돼 있어도 재고수량과 비교하지 않는다. 규격·품명·과거 자료를 단위로 추정하지 않는다.

권장 파생 상태는 다음과 같다.

```js
{
  orderUnitUnspecified: boolean,
  inventoryUnitUnspecified: boolean,
  inventoryUnitMismatch: boolean,
  quantityComparable: boolean
}
```

기존 `unitUnspecified` 소비자가 있으면 `orderUnitUnspecified || inventoryUnitUnspecified` 의미의 호환 필드로 유지한다. 비교 불가 시 상품합계의 단위 혼합 의미를 보존하고 배정·잔량·구매필요·대사 차이를 계산하지 않으며 상태는 `단위 확인`으로 표시한다. 다른 정상 상품의 계산은 계속한다.

## 8. 좌측 담당자별 건수

담당자별 건수는 상품행 수량이나 상품행 개수가 아니라 `getDeliverySummaryRows()`가 반환하는 주문서별 배송건을 기준으로 한다.

계산 순서는 다음과 같다.

1. 전체 주문서별 배송건을 구한다.
2. 현재 창고 조건을 적용한다.
3. 현재 지역 조건을 적용한다.
4. 담당 조건은 건수 계산에서 제외한다.
5. 남은 주문서를 담당별로 한 번씩 집계한다.

따라서 담당 A를 선택한 상태에서도 같은 창고·지역 범위의 담당 B·미지정·혼합 버튼을 계속 표시한다. 다른 담당 버튼을 누르면 담당 조건만 교체된다.

혼합 담당 주문은 `혼합` 한 건으로만 계산하고 각 담당자 건수에 중복 추가하지 않는다. 미지정 주문은 숨기지 않는다. 건수 버튼과 담당 select는 같은 `state.deliveryManagerFilter`를 사용하며 배정값을 변경하지 않는다.

권장 순수 함수 경계는 다음과 같다.

```js
filterDeliveryRowsByWarehouseAndRegion(rows, warehouseFilter, regionFilter)
buildManagerDeliveryCounts(scopedRows)
```

## 9. 검색과 0건 상태

### 9.1 검색 조작

- 검색 입력 앞에는 값 유무와 관계없이 `검색`을 표시한다.
- `검색 해제` 버튼은 `state.searchQuery`와 입력값만 비운다.
- 검색 해제는 규격·창고·담당·열 조건·정렬·양식·열폭·편집값을 바꾸지 않는다.
- F2는 기존 결과 보기 초기화 범위를 유지한다.
- 로그인명·작업자명·담당자명을 검색 기본값으로 주입하지 않는다.

### 9.2 0건 원인 판정

중앙 빈 상태는 아래 우선순위로 판정한다.

| 상태 | 표시 문구 | 제공 조작 |
|---|---|---|
| 원본 없음 | `자료를 불러오면 작업표가 표시됩니다.` | 관련 불러오기 |
| 재고만 있음 | 재고표와 `주문 미등록` | 주문서 불러오기 |
| 검색으로 0건 | `검색 결과 0건` | `검색 해제` |
| 검색 외 필터로 0건 | 적용 중인 조건과 `조회 결과 0건` | `필터초기화 F2` |
| 실제 원본이 0행 | 파일명과 `읽은 자료 0건` | 파일 교체 |

일부 주문 상품만 재고에 없으면 전체 빈 상태로 만들지 않고 해당 행의 `재고자료 없음`을 유지한다. 재고 0, 재고 미등록, 주문 미등록을 같은 값으로 합치지 않는다.

복구된 검색·필터가 적용 중이면 중앙 상단에 활성 조건을 보이게 표시한다. 사용자가 인식하지 못하는 복구 조건으로 0건 화면을 만들지 않는다.

## 10. 업무 상태 표시

가시 UI에서 `System.IO` 명칭, 콘솔 프레임, 점멸 커서를 제거한다. 다음 기존 상태 노드는 기능적으로 재사용할 수 있다.

- `systemMessage`
- `validationBox`
- `systemViewNote`
- `localSaveStatus`
- `cloudStatus`

단, 사용자에게는 다음 두 위치로 투영한다.

1. 파일 버튼 인접 상태: 파일명, 읽은 건수, 오류 건수
2. 하단 작업바 상태: 분석·임시저장·완료본 저장 결과

상태는 실제 결과 이후에만 성공으로 표시한다.

| 상태 | 예시 |
|---|---|
| 파일 읽는 중 | `주문서 읽는 중` |
| 파일 읽기 성공 | `미출고현황.xlsx · 86행` |
| 부분 실패 | `적용 278건 · 오류 2건` |
| 분석 중 | `출고분석 실행 중` |
| 편집 후 미저장 | `변경사항 임시저장 대기` |
| 임시저장 성공 | `임시저장 완료 · 14:22` |
| 저장 실패 | `저장 실패 · 작업은 화면에 보존됨` |
| Cloud 저장 성공 | `완료본 저장 완료` |

`PENDING` 접수, 네트워크 요청 시작, 파일 선택만으로 완료를 표시하지 않는다. 실행 오류는 업무 검토용 시스템 메시지 열에 넣지 않는다. 운영 화면에서 `이번 개발 범위`, `승인 전`, `테스트용` 같은 개발 진행 문구를 표시하지 않는다.

## 11. 데이터·저장·실행 경계

이번 개발은 화면 조작 위치, 조회 표시와 주문·재고 비교 안전성 보완이다. 다음 계약을 변경하지 않는다.

- `shipping-workspace/v2`
- `ONEAPPShippingRecoveryDB` v1과 `recoveryRecords`
- `ONEAPPShippingResultDB` v1과 출고결과 Store
- ORDER Q 주문 Read Adapter와 OrderOps 출고결과 쓰기 소유권
- 기존 Cloud plan action·payload·Revision·충돌 처리
- `substitutionHistory`, `systemHistory` append-only 이력
- 원본 source matrix와 SHA-256 검산
- Excel 출력 시트·열·수식·인쇄영역
- 단위가 명시돼 비교 가능한 정상 상품의 주문수량·금액·재고·잔량·구매필요 계산

열 key 이전은 로컬 UI 설정의 호환 정규화이며 업무 데이터 schema migration이 아니다. 재고 단독 창고별 표시는 이미 보존된 source matrix의 읽기 투영이고 신규 원본 필드 저장이 아니다.

버튼 이동은 명령의 의미를 합치지 않는다.

- `출고분석`: 현재 자료 계산
- `저장 F8`: 기존 Cloud 완료본 저장
- `출고확정`: 기존 출고결과 확정 명령
- `이전복구`: 최신 검증 정상 임시저장 복구

검색·필터·메뉴·패널 폭 변경은 네트워크 요청이나 업무 저장을 실행하지 않는다.

## 15. PR과 배포

잔여 범위는 화면 조작과 같은 테스트 계약이 함께 바뀌므로 한 PR로 구현한다. 공통 레이아웃의 별도 원인이 발견되지 않으면 OrderOps 앱 파일 밖으로 변경을 확대하지 않는다.

병합 전 확인:

- PR head가 검증한 commit과 일치
- 필수 CI 전부 성공
- 변경 파일이 본 명세 범위를 벗어나지 않음
- 기존 완료 항목 회귀 없음

운영 확인:

- Pages 배포 run 성공
- 운영 `orderops/list.html`과 엔진 버전이 병합 SHA와 일치
- 4→6→6열·좌측 담당 변경·재고 동적 열·단위 공란과 앱헤더·하단 작업바·검색·담당 건수·창고코드 확인
- 운영 쓰기 검증은 격리 합성자료만 사용

## 16. 롤백

- UI 롤백은 헤더·메뉴·하단 작업바·상태 표시 commit을 되돌리되 기존 이벤트 ID와 저장키를 유지한다.
- `창고코드` 별칭 롤백은 파서 별칭과 관련 테스트만 되돌린다. 기존 관리자 저장 매핑을 삭제하지 않는다.
- 안정 열 key 롤백은 이전 위치 key 읽기 호환을 남기고 사용자 열 설정을 삭제하지 않는다.
- 재고단위 비교 롤백은 코드만 되돌리며 저장된 원본·분석본·출고결과를 다시 계산해 덮어쓰지 않는다.
- 코드 롤백은 이미 생성된 로컬 복구·Cloud 완료본·출고결과·이력을 삭제하거나 이전 값으로 자동 변경하지 않는다.
- 공통 작업영역 파일을 변경했다면 앱 전용 변경과 분리해 독립 revert할 수 있어야 한다.
