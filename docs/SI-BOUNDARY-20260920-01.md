## 1. 개발 목적

**스마트입력에서 원본 자료를 받아 매칭·편집·검토하고, 입력자료와 견적서를 완성해 원하는 Excel을 빠르고 안정적으로 만드는 것이 이번 개선의 목적이다.**

이를 위해 분산된 기존 소스를 업무 역할별로 합치고, 큰 화면 본체에 섞인 업무 처리를 옮긴다. 같은 자료를 반복해서 읽고 계산하는 경로를 줄이고, 입력·견적·출력과 선택적 외부 연동의 책임을 명확히 한다.

개선의 성공은 다음 결과로 판단한다.

1. 입력·견적·Excel 작업이 다른 업무 앱의 정상 동작을 선행조건으로 요구하지 않는다.
2. 기능을 수정할 위치가 명확하고, 불필요한 연결 파일과 중간 호출이 줄어든다.
3. 기존 자료·기능·출력 결과·복구 계약이 보존된다.
4. 실측에서 확인된 입력 지연과 반복 처리 병목이 개선된다.

**파일 수 감소와 체감 속도 개선은 별도로 검증한다. 총 파일을 8개로 맞추거나, 모든 기능을 본체 한 파일에 모으는 작업으로 진행하지 않는다.**

## 2. 앱의 역할과 개발 범위

### 2.1 스마트입력의 기본 업무

`원본 입력 → 해석·매칭 → 편집·검토 → 입력자료 완성 → Excel 출력`

견적서는 스마트입력 안에서 작성·저장·조회·수정·선택 업데이트·출력까지 완료한다. 입력자료 완성은 외부 시스템에 거래가 공식 등록됐다는 뜻이 아니다. 새로운 입력 완료 버튼이나 별도의 필수 승인 단계를 추가하지 않는다.

### 2.2 선택적 연동 업무

`완성자료 전달 → 수신 결과 확인 → 기존 연동 전표 조회·재사용`

스마트입력은 전달 요청과 결과 표시를 담당한다. 공식 전표·거래·재고 반영은 수신 앱의 기존 책임을 유지한다.

**초기 진입·일반 입력·자동저장·Excel 출력은 공식 전표 등록·원장 조회·동기화를 시작하지 않는다. 자료 전달·연동 전표 조회·외부 기준정보 갱신 등 해당 기능을 실행할 때만 필요한 연결을 준비한다. NEXUS 안에서 실행됐다는 이유만으로 연동을 자동 실행하지 않는다.**

별도의 모드 선택 화면을 추가하지 않는다. 기존 기능의 실행 동작을 기준으로 연결을 준비하고, 버튼 표기뿐 아니라 내부 자동 실행 경로도 이 조건에 맞춘다. 로컬 Snapshot·캐시 복구와 견적 출력에 필요한 Settings 가격·매핑의 읽기 전용 소비는 외부 갱신·원장 조회·동기화와 구분해 기존 owner Read Adapter로 유지한다.

NEXUS 공통 UI·호스트의 준비 상태, 앱 이동 전 저장, 테마·인쇄 연결은 선택적 업무 연동과 구분해 화면 연결 역할에 유지한다. SmartInput Core의 기본 실행은 공통 UI·호스트·인증 응답을 선행조건으로 삼지 않는다. 외부 명령의 기존 권한 확인은 해당 실행 경계에 유지한다.

### 4.1 호출과 상태 변경 원칙

- 업무자료 변경은 `화면 → 입력 엔진의 변경 기준 → 해당 기능 처리 → 변경 결과 표시`를 기본으로 한다.
- 파일·보고서·연동 버튼은 필요한 기능만 선택 로딩한다. 기존 입력·문서 처리 규칙을 하나의 기준으로 통합하더라도 모든 기능을 초기 import하지 않는다.
- 모듈은 필요한 값·작업 문맥·콜백을 명시적으로 받는다. 기능 모듈이 화면 본체를 다시 import하거나 화면 전역 상태에 몰래 접근하는 순환 구조를 만들지 않는다.
- 포커스·선택·스크롤 등 화면 상태 변경은 업무자료 버전을 바꾸거나 재파싱·전체 합계 계산을 유발하지 않는다.
- 엔진은 업무자료 변경의 단일 기준이다. 파서·표·견적·출력에 별도 변경 엔진을 만들지 않는다.
- 기존 `smartinput-contract.js`의 정규화·검증·ID·저장키 계약을 엔진 정리의 출발점으로 검토한다. 전역 script 계약을 변경해야 하면 소비자와 로딩 순서를 먼저 확인한다.

### 4.2 별도 유지가 가능한 파일

Worker, OCR 처리, 대용량 필드 정의, 외부 라이브러리, 테스트와 서로 다른 로딩 시점의 기능은 별도 유지한다. 견적·출력처럼 합치면 수정 부담이나 초기 로딩량이 커지는 업무는 역할 안에서 소수 파일을 유지할 수 있다.

유지 이유는 `실행 환경`, `로딩 시점`, `외부 소비자 호환`, `업무 규모` 중 해당 근거와 실제 소비자로 기록한다. 파일이 작거나 이름에 `legacy`·`v2`가 있다는 이유로 삭제하지 않는다.

## 6. 독립 입력과 견적 처리

### 6.1 입력·매칭의 자체 처리

- 필요한 텍스트 추출·행 해석을 스마트입력의 입력 역할에서 소유한다. 다른 앱의 원장·재고·거래 엔진을 복사하지 않는다.
- 매칭은 현재 입력값, 사용자가 확정한 매칭사전, 유효한 로컬 기준정보·캐시를 사용한다. 상품 색인은 자료 세대별로 재사용하고 매 입력행마다 전체 저장소를 다시 읽지 않는다.
- 상품·거래처는 기존 owner Read Adapter로 읽고, 견적 가격·매핑은 Settings Read Adapter로 읽기 전용 소비한다. owner 원시 저장소 접근·필드를 새로 확장하거나 Settings 키를 생성·초기화·저장·동기화하지 않는다. 작업용 캐시는 원본 권위를 갖지 않으며 회사 범위와 문서·자료 세대를 조회부터 비동기 결과 적용까지 유지한다.
- 명시적 기준정보 전체 갱신은 거래처·상품·창고·담당자·프로젝트·필드정의 6개 영역을 한 불변 세대로 준비·검증한 뒤 활성 세대 포인터를 원자적으로 교체한다. 부분 실패 시 이전 세대·검색어·열린 작업본을 유지하고, 새 세대를 열린 작업본에 자동 덮어쓰지 않는다.
- 기존 고객·원본별 매칭사전과 이력은 소유 저장소에 보존한다. 독립 입력에 필요한 복사본·조회 계약·갱신 시점을 정하고, 외부 조회가 필요한 이력은 선택 연동에서 준비한 결과만 사용한다. 원장 조회 실패를 0건으로 취급하거나 기존 사전을 삭제하지 않는다.
- 외부 자료가 없어 근거가 부족한 항목은 미매칭으로 유지한다. 존재하지 않는 상품 ID, 단위 환산, 가격을 추정해 확정하지 않는다.
- 파서 소유 위치를 옮길 때 원본 메시지 키, 취소·정보 메시지 구분, 속성·단위·문맥 참조와 원본 증거를 유지한다.

### 6.2 견적의 독립 완결

- 작성·불러오기·저장·조회·수정·선택 업데이트·Excel 출력은 스마트입력의 기본 기능으로 유지한다.
- 선택 회사와 선택 견적서에만 기존 저장 계약을 적용한다. 견적 전환 시 각 견적의 미저장 작업을 보존한다.
- 기존 값과 Revision을 확인한 저장, 견적 ID·행 ID, 마지막 Excel 결과와 자동저장 journal의 의미를 유지한다.
- 외부 마스터 적용과 동기화 결과를 견적 로컬 저장 성공과 구분한다. 외부 적용은 실제 사용자·회사·권한 증거와 기존 명령 계약으로 검증하며 로컬 편집용 기본 회사·actor로 대체하지 않는다. 외부 적용 실패로 저장된 견적이나 현재 편집을 되돌리지 않는다.
- 과거 연동 자료는 현재 지원하는 읽기·복구·재사용 경로를 유지한다. 현재 독립 견적 구조를 과거 연쇄 저장 방식으로 되돌리지 않는다.

## 7. 작업 버전과 비동기 결과 보존

새로운 필수 UI 단계 없이 내부 처리 기준을 명확히 한다. 작업 버전은 현재 편집본의 변경 순서를 뜻하며, 기존 DB Revision·외부 요청 ID를 대체하지 않는다.

1. 업무자료 변경 시 해당 문서·견적의 작업 버전을 갱신한다. 기존 ID와 원본 연결은 유지한다.
2. 출력·전달 시작 시 자료, 설정·가격 규칙·기준정보 버전을 묶은 처리 스냅샷을 고정한다.
3. 완료 결과에는 사용한 작업 버전과 처리 범위를 내부 기록으로 연결한다. 화면에서 현재 자료와 결과가 다른 경우 구분할 수 있게 한다.
4. 처리 중 새 편집이 발생하면 이전 결과로 현재 행·상태를 덮지 않는다. 결과 기록은 해당 제출 버전에 귀속한다.
5. 다건 전달의 일부만 성공하면 성공·실패·확인 중 항목을 구분한다. 성공한 항목을 새 요청으로 다시 제출하지 않는다.
6. 응답을 받지 못한 경우 기존 요청키로 결과를 먼저 확인한다. 확인할 계약이 없거나 조회가 실패하면 결과 미확정 상태를 보존하고 새 거래 생성을 자동 실행하지 않는다.

입력자료 완성, Excel 생성, NEXUS 접수, ERP 반영은 서로 다른 상태다. NEXUS 접수는 기존 수신 대상의 접수·명령 결과를 뜻하며 새 중앙 접수 서버·전역 큐를 뜻하지 않는다. 공식 자료 전달은 기존 회사·권한·Revision·멱등성·원자성과 기능별 로컬 완료·서버 확정·후행 동기화 조건을 유지하며 로컬 확정을 임의로 서버 응답 대기로 바꾸지 않는다. 출력 파일에 성공 표시가 있다고 공식 거래 반영을 추정하지 않는다.

### 8.2 전후 실측

같은 PC·브라우저 버전·대표자료·설정으로 변경 전과 후를 비교한다. 최초 진입과 재진입, 최초 실행과 캐시 재사용을 구분한다. 운영 DB를 지우거나 사용자 거래를 만들어 성능을 측정하지 않는다.

| 측정 대상 | 측정 구간·기록 |
|---|---|
| 최초·재진입 | 진입부터 입력 가능 시점, 복구 완료 시점, 초기 JS 요청·전송량, 외부 요청·저장소 접근 |
| 셀 편집 | 입력 이벤트부터 다음 표시 프레임, 재계산 행·그룹 수, 긴 작업 발생 |
| 이동·스크롤 | 프레임 지연, 표시행 수, 불필요한 파싱·계산 실행 여부 |
| 견적·탭 전환 | 선택부터 표시 완료, 상세·사진 읽기 횟수, 캐시 적중·무효화 |
| 보고서 | 계산, 시트 구성, 파일 생성 구간을 각각 기록하고 전체 시간도 기록 |
| 저장·메모리 | 자동저장 지연·대기 작업 수, 반복 작업 뒤 메모리 추이와 잔존 객체·이벤트 증가 |

대표자료는 소·중·대 규모와 실제 사용 자료로 고정한다. 각 자료의 식별값·행 수·설정과 반복 횟수를 기록하고, 중앙값·상위 지연값·실패 횟수를 함께 제출한다. 기존 `ONEAPP_SMARTINPUT_PERFORMANCE.snapshot()` 계측을 우선 활용하며 원문 업무값을 측정 로그에 남기지 않는다.

`APP_ARCHITECTURE.md` 3.5절의 기존 기준을 해당 구간에 적용한다. 클릭·터치 시각 피드백은 p95 100ms 이하, 공통 계층 Warm 차단은 p95 150ms 이하, 검증된 로컬 데이터 Warm 표시는 p95 500ms 이하, Warm 앱 이동·사용 가능은 p95 1초 이하로 유지한다. 검증된 로컬 자료가 있는 Warm 진입에서 실제 자료 표시 전 업무 Gateway 요청은 0회, 서버 장애 중 허용된 로컬 업무 성공률은 100%, 서버 오류의 정상 0건 표시와 새 서버 값의 활성 작업본 자동 덮어쓰기는 각각 0건이다.

절대 KPI를 초과하거나 기존 p95보다 10%를 넘게 악화되면서 절대 증가도 100ms를 초과하면 원인을 확인하고 조정·격리·롤백을 검토한다. 기준선부터 초과한 항목은 별도 기록하고 개선율만으로 통과 처리하거나 기준을 임의로 낮추지 않는다. 이 수치는 해당 화면·표시·이동·장애 격리 구간의 기준이며 모든 보고서의 생성 시간을 1초로 제한하는 기준이 아니다.

병목별 추가 수치 목표만 변경 전 측정을 마친 뒤 성능 수정 전에 확정한다. 개선율·메모리 절감률·공수를 근거 없이 선기입하지 않는다. 동일 처리를 유지한 구조 이동의 결과를 속도 개선으로 보고하지 않는다.

## 10. 개발 순서와 단계별 완료 근거

동일 작업 ID 아래 작은 기능 단위로 구현·검증·커밋한다. 파일 이동·통합과 계산 방식·성능 수정은 구분한다. 같은 파일을 여러 작업이 동시에 수정하지 않도록 소유 범위를 정한다.

### 묶음 1. 기준 고정과 작은 연결 정리

1. 최신 main·진행 중 변경·기존 테스트 상태를 확인하고 기준 소스와 복구점을 기록한다.
2. 대표 입력·출력·복구 자료와 비교 결과, 파일·참조·초기 로딩 및 성능 기준을 고정한다.
3. 파일·함수 소유권과 전체 소비자·로딩 시점을 조사해 통합 대응표를 작성한다.
4. 행 보조·입력 연결 파일부터 기존 입력 역할로 흡수한다. 활성 참조를 전환한 뒤 사용하지 않는 구현만 제거한다.
5. 선택 로딩 실패·재시도·새 입력 중 늦은 결과·기존 캐시 화면 재로딩을 검증한다.

**완료 근거:** 실제 파일·참조 전후표, 보존 동작 테스트, 동일 입력·출력·복구 결과, 초기 로딩 증가 여부와 예외 사유.

### 묶음 2. 본체 정리와 독립 업무 완성

1. 본체의 업무자료 변경을 입력 엔진 기준으로 정리하고 화면 동작과 구분한다.
2. 입력 해석·로컬 매칭·원본 증거·양식 처리를 입력 역할로 통합한다.
3. 견적 관리·출력·저장·기준정보를 책임별로 옮기고 중복 구현을 제거한다.
4. 작업 버전과 출력·전달 스냅샷을 연결한다. 기존 ID·Revision·요청키는 유지한다.
5. 직접 URL과 NEXUS 호스트 진입을 각각 확인하고, 공통 자산·외부 업무 앱·기준정보·로그인 서버 실패와 세션 부재에서도 허용된 직접입력·복구·견적·Excel 완료 및 앱 이동 전 저장 보존을 확인한다.

**완료 근거:** 주요 기능의 수정 위치표, 순환 의존 없음, 독립 입력의 원장 접근 없음, 현재 견적·DB v5·출력 계약 보존, 외부 실패 중 작업 지속.

### 묶음 3. 선택 연동 호환과 성능 개선

1. 기존 전달·수신 결과·관련 전표 조회·재사용을 선택 연동 역할로 정리한다.
2. 재시도·응답 유실·부분 성공·동시 편집에서 요청 결과와 최신 편집의 분리를 검증한다.
3. 통합이 끝난 기준에서 병목을 다시 측정하고 반복 조회·재계산·렌더·저장의 원인을 수정한다.
4. 같은 대표자료로 최종 전후 성능과 정확성·복구를 검증하며 8.2절의 기존 NEXUS 기준과 추가 병목 목표를 각각 판정한다.
5. 검증이 통과한 배포 단위별로 기존 운영 경로에서 버전·기본 실행을 확인하고 보고서를 제출한다.

**완료 근거:** 연동 호환과 요청 상태 증거, 실제 성능 측정표, 남은 병목, 배포·운영 기술 확인 및 롤백 가능한 복구 근거.

## 12. 배포·중단·롤백과 제출물

### 12.1 배포와 중단

- 기능을 임시로 제거해 전달·조회 등 기존 운영을 끊지 않는다. 활성·동적·외부 참조가 대체된 뒤 구 구현을 제거한다.
- 기능 묶음마다 자산 버전과 캐시 전환을 함께 확인한다. 기능 미사용 시 로딩량 증가를 통합의 불가피한 결과로 간주하지 않는다.
- 정상 출력의 수량·금액 변경, 작업 유실, 독립 경로의 원장 쓰기, 저장 계약 손상이 확인되면 해당 묶음 배포를 중단한다.
- 별도 테스트 뷰어를 만들지 않는다. 같은 앱의 기존 실행 경로로 검증하고, 승인된 배포 후 기존 운영 사이트에서 핵심 실행을 확인한다.

### 12.2 롤백

- 기준은 이번 작업 직전의 호환되는 운영 코드다. 사용자 데이터·정상 거래기록·확정 Revision·접수기록은 삭제하지 않는다.
- 기존 독립 견적·DB v5 자료를 읽을 수 있는 복구 경로를 유지한다. 과거 연동 견적 writer나 오래된 전체 DB 백업으로 되돌리지 않는다.
- 저장 위험이 있는 경우 기존 읽기 전용 복구 경로(`?estimateRecovery=readonly`)의 적용 가능성과 동작을 검증한다. 단순 코드 롤백을 데이터 복원으로 간주하지 않는다.
- 실제 데이터 복원이 필요한 상황은 백업·현재값·변경 후 편집을 비교하는 별도 절차로 다루며, 이번 파일 통합을 근거로 일괄 덮어쓰지 않는다.

### 12.3 최종 제출 보고서

1. 작업 ID, 기준·최종 SHA, 변경 범위, 단계별 commit·PR·배포 상태.
2. 기존 파일·함수와 통합 후 소유 위치·소비자·로딩 시점의 대응표.
3. 동일 집계 기준의 파일 수·참조 수·초기 로딩 전후표와 별도 유지 파일의 이유.
4. 주요 기능별 수정 위치와 내부 호출 구조.
5. 대표자료 입력·출력 셀 비교, 견적·자동저장·복구·실패·연동 검증 결과.
6. 같은 조건의 시간·메모리 실측, 개선된 병목과 남은 병목.
7. 구조·정확성·독립성·성능·운영의 개별 판정과 미검증 항목.
8. 롤백 기준·복구 확인 결과와 범위 밖 후속 검토사항.

이 문서는 개발 목표와 수행 기준을 정한다. 최종 삭제 파일 수, 성능 개선율, AI 사용량 절감률, 공수와 배포 완료를 미리 확정하지 않는다.
