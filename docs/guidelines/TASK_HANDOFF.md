# NEXUS 작업지시서 작성 기준

Version: 1.0.0
Last Updated: 2026-09-08

## 1. 적용 원칙

인계가 필요한 경우 다음 작업자에게 그대로 전달할 수 있는 실행 명령문을 작성한다. 단순 질문이나 현재 작업방에서 완료한 일에 불필요한 후속 작업을 만들지 않는다.

작업 설정사항 가이드는 사용자에게 제시하는 권고이며, 작업지시서는 다음 담당자의 실행 기준이다. 권고를 승인으로 바꾸지 않고 사용자의 실제 승인 문장과 승인된 단계를 명시한다. 명세 작성 승인을 코드 수정·병합·배포 승인으로 확대하지 않는다.

이전 대화를 읽지 않아도 이해할 수 있게 작성한다. 파일·저장소·명세·PR 등은 확인 가능한 위치와 기준 버전을 적는다. 다른 환경의 로컬 경로 접근이나 채팅 문맥의 자동 공유를 가정하지 않는다. 사실을 확인할 수 없으면 미확인으로 표시하고 확인할 항목을 지정한다.

아래는 작성용 틀이다. 실제 전달문에서는 대괄호를 채우고, 불필요한 항목은 제거하며, 필요한 내용이 빠지지 않는 범위에서 짧게 작성한다. 기술적 실행 순서를 과도하게 고정하지 않는다.

## 2. 명령문 형식

```text
[작업명 / 기존 작업 ID가 있으면 함께 기재]

당신은 이 작업의 [담당 역할]이다.
다음 목적과 승인 범위에 따라 작업하라.

1. 목적
[해결할 문제와 사용자가 얻어야 할 결과]

2. 작업 범위
수행할 일: [구체적인 실행 항목]
유지할 사항: [기존 기능·업무규칙·데이터·호환성]
제외할 사항: [변경하지 않을 대상]

3. 기준 자료와 현재 상태
[저장소·파일·확정 명세·PR의 확인 가능한 위치]
[기준 커밋·명세 버전·작업 브랜치·기존 변경 상태]
[확정사항·미결정 사항·미검증 사항]
저장소 작업이면 AGENTS.md와 변경 관련 아키텍처 계약을 확인하라.
전달 기준과 실제 상태가 다르면 영향부터 확인하고 기존 변경을 보존하라.

4. 승인 범위
사용자 승인 원문: [실제 승인 문장]
승인된 단계: [분석·문서·코드 수정·테스트·Git·PR·병합·배포 중 해당 항목]
승인되지 않은 단계는 실행하지 마라.

5. 실행 원칙
승인 범위 안의 구현 방법과 기술적 처리 순서는 직접 판단하라.
원본과 다른 작업자의 변경사항을 보호하라.
범위 밖 문제는 자동으로 수정하지 말고 발견 근거와 영향을 기록하라.
새로운 업무정책·범위 변경이 필요하면 쟁점과 권고안을 보고하라.
실제 중대한 위험이 있으면 해당 작업을 보류하고 증거를 보존하라.

6. 완료조건
[대표 작업 사례와 기대 결과]
[필요한 검증과 산출물]
작업량이나 코드 작성 여부가 아니라 요구한 결과의 충족 여부로 확인하라.

7. 결과 보고
완료·미완료 상태와 목적 충족 여부를 먼저 보고하라.
변경 내용, 결과물 위치, 검증 증거, 남은 위험을 제시하라.
직접 실행한 검증·증거 검토·미검증을 구분하라.
배포가 포함됐다면 배포 버전과 운영 확인 결과를 함께 보고하라.
다음 인계가 필요하면 현재 상태와 남은 작업을 같은 기준의 명령문으로 전달하라.
```

## 3. 인계 전 확인

목적·범위·승인·완료조건이 서로 맞는지, 다음 담당자가 기준 자료에 접근할 수 있는지, 이전 작업의 브랜치·변경·증거가 보존되는지 확인한다. 지정 역할과 실제 실행 도구·권한을 혼동하지 않는다. 인계문을 작성한 상태와 실제 전송·접수·실행 상태를 구분한다.
