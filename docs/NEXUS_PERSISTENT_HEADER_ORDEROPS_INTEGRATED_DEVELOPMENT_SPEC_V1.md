## 1. 목적

NEXUS 글로벌헤더를 유지한 채 하단의 업무 앱만 전환하는 통합 화면을 구축하고, 동시에 진행되는 출고관리 잔여 개선을 안전하게 병합한다.

핵심 원칙은 다음과 같다.

1. 공통헤더와 출고관리 업무 개선은 병행 개발할 수 있다.
2. 공통헤더 담당은 출고관리의 테이블·필터·계산·저장 오류를 수정하지 않는다.
3. 출고관리 담당은 공통 화면 호스팅·앱 전환·부모 이력을 구현하지 않는다.
4. 출고관리 업무 수정이 병합된 최신 파일에 임베드·이탈 연결만 추가한다.
5. 이전 사본으로 `orderops/list.html` 또는 다른 앱 파일 전체를 교체하지 않는다.
6. 7개 앱 연결과 홈 기본 진입 전환은 통합검증을 통과한 뒤 순차 반영한다.

이 문서는 개발 실행의 기준이다. 문서 작성만으로 생산 소스 변경·PR·배포가 완료된 것으로 보지 않는다. 사용자가 개발을 지시하면 본 명세의 PR 순서, 병합, Pages 배포와 운영 기술검증까지 수행한다.

## 6. 목표 아키텍처

### 6.1 부모 통합 화면

신규 공식 통합 화면 후보는 `nexus/workspace.html`이다.

```text
body
├─ global-header                 최초 1회 생성·유지
└─ nexus-workspace-host
   ├─ transition-status         하단 영역에만 표시
   ├─ app-frame                 항상 1개
   └─ load-error-actions        재시도·독립 앱 열기
```

부모가 소유하는 것은 글로벌헤더, 앱 선택, 허용 경로, 최상위 이력, 테마 전달, 전환 상태다. 업무자료·저장소·계산·인증 성공·앱 준비 상태는 소유하지 않는다.

### 6.2 단일 iframe

- 활성 업무 iframe은 항상 최대 1개다.
- 이전 앱 iframe을 숨겨 보관하지 않고 안전한 이탈 완료 후 같은 frame을 탐색한다.
- 새 앱이 준비되기 전까지 글로벌헤더는 유지하고 하단에만 로딩 상태를 표시한다.
- iframe `load`는 문서 로드 신호일 뿐 업무 준비·저장 성공 신호가 아니다.
- 외부 URL, `javascript:`, `data:`, 알 수 없는 HTML은 frame에 열지 않는다.
- 현재 운영 응답에 frame 차단 헤더가 없더라도 배포 단계에서 CSP `frame-ancestors`와 `X-Frame-Options`를 다시 확인한다.

### 6.3 독립 실행

7개 공식 앱 URL은 그대로 유지한다. 직접 URL·북마크·새 창에서는 기존 글로벌헤더와 앱 기능을 제공한다.

임베드 판정은 URL 플래그만으로 하지 않는다. 다음 조건을 모두 만족해야 한다.

1. 명시적 `embed=nexus-workspace-v1` 표시
2. `window.parent !== window`
3. 부모 origin이 현재 origin과 일치
4. 실제 부모 frame이 NEXUS 호스트로 확인됨

판정은 첫 화면 표시 전에 실행한다. 독립 실행을 임베드로 오판해 글로벌헤더와 상단 공간을 제거하면 안 된다.

## 7. 높이·스크롤·헤더 계약

### 7.1 부모 높이

- 글로벌헤더: 데스크톱 64px, 모바일 104px
- iframe 영역: `100dvh - 실제 글로벌헤더 높이`
- 부모 body는 업무 화면용 별도 상단 padding을 다시 추가하지 않는다.
- 글로벌헤더 DOM·높이·배경·탭 그룹은 앱 전환 중 재생성하지 않는다.

### 7.2 자식 높이

- 임베드 자식은 글로벌헤더만 숨기고 관련 `nexus-ui-mounted` 상단 보정을 0으로 한다.
- 앱헤더 56px와 앱 내부 작업영역은 유지한다.
- `--nexus-ui-header-height`, `100dvh`, sticky·fixed·print offset을 앱별로 대조한다.
- 부모와 자식이 글로벌헤더 높이를 각각 차감하는 이중 차감을 금지한다.
- 출고관리의 좌측·중앙·우측 패널, 하단 작업바, 표 내부 스크롤은 임베드에서도 독립 실행과 같은 작업 높이를 가져야 한다.

### 7.3 탭 이동

- 선택 탭이 현재 보이는 범위에 있으면 `scrollLeft`를 바꾸지 않는다.
- 가려진 경우에만 필요한 최소 거리만 이동한다.
- resize 때마다 무조건 가운데 정렬하지 않는다.
- 앱 이동 전후 사용자가 만든 탭 스크롤 위치를 가능한 범위에서 유지한다.

### 7.4 출고관리 반응형 패널

좌측 220px·우측 180px·중앙 작업표를 390px에서 같은 행에 강제로 배치하지 않는다. 세 섹션은 같은 부모와 DOM 순서를 유지하되 가용 CSS 폭에 따라 다음 배치만 바꾼다.

| 가용 CSS 폭 | 배치 |
|---|---|
| 1100px 이상 | 좌측·중앙·우측을 같은 행에 배치하고 좌우 독립 너비 조절 제공 |
| 640~1099px | 좌측과 가용 폭 중앙을 같은 행에 배치하고 좌측 너비 조절 유지, 우측은 중앙을 밀지 않는 너비 조절형 overlay sheet로 열기 |
| 639px 이하 | 좌측을 전체 폭 상단 행, 중앙을 전체 폭 하단 행에 배치하고, 우측은 overlay sheet로 열기 |

- 390px에서는 좌측이 `display:none`이 되지 않는다. 필터와 4열 표는 상단 영역 안에서 자체 스크롤하고 중앙 표는 남은 영역에서 자체 가로·세로 스크롤한다.
- 모바일 좌측 영역은 최대 `38dvh`로 제한해 중앙 표에 접근 가능한 높이를 남긴다.
- 640~1099px의 좌측은 최소 220px, 중앙은 최소 320px을 우선 보장하는 가용 범위에서 resize한다. 우측 overlay는 최소 180px에서 `min(420px, calc(100% - 16px))`까지 독립 resize한다.
- 639px 이하의 우측 overlay는 `width: min(320px, calc(100% - 16px))`로 제한하고 좌우 resize handle을 비활성화한다.
- breakpoint 전환은 저장된 데스크톱 좌우 폭을 덮어쓰지 않으며, 넓은 화면 복귀 시 이전 폭을 복원한다.
- 우측의 닫힘·열림 상태와 내부 입력·스크롤은 배치 모드 변경 뒤에도 보존한다. 사용자가 우측을 다시 열면 화면 갱신만으로 닫지 않는다.
- DOM·ARIA 순서는 좌측→중앙→우측을 유지하며, `주문 목록`, `분석표`, `우측 열기` 바로가기로 키보드와 터치 이동을 제공한다.

## 8. 경로와 이력

### 8.1 부모 URL

```text
nexus/workspace.html?app=<등록된 앱 ID>&route=<인코딩한 상대 경로·쿼리·해시>
```

- `app`은 공통 정적 앱 목록의 ID만 허용한다.
- `route`는 해당 앱과 승인된 하위 화면의 같은-origin 상대 경로만 허용한다.
- 업무자료 전체, access token, 사용자 개인정보를 URL에 넣지 않는다.
- 잘못된 route는 임의의 주문·회사·전표로 치환하지 않고 오류와 안전한 앱 선택을 표시한다.

### 8.2 이력 권위

부모가 최상위 앱 전환 이력의 권위다.

- 사용자 앱 탭 선택: 부모 `pushState`
- 현재 자식의 같은 화면 상태 교체: 부모 `replaceState`
- 뒤로·앞으로: 저장된 부모 상태를 검증한 뒤 동일 이탈 절차 수행
- 새로고침: URL의 앱과 route 복원
- 이탈 취소: 현재 화면과 URL을 원래 상태로 되돌리고 추가 history loop를 만들지 않음

출고관리의 `orderId`, `returnTo`, `focus`와 ORDER Q의 `from`, `to`, `q`, `view`는 자식 route 변경 시 부모에 반영한다. 부모와 자식이 같은 이동을 각각 push해 이력 두 개를 만들지 않는다.

### 8.3 내부 링크

일반 앱·하위 화면 이동은 `nexus-navigation.js`의 검증 API를 사용한다. 전역 `window.location`을 monkey patch하지 않는다.

- 다운로드·파일 선택·외부 링크·명시적 새 창은 기존 동작 유지
- 통합 화면 안의 허용 내부 링크는 부모 탐색 요청
- 독립 실행에서는 기존 직접 경로 이동
- Settings의 `mode=iframe` 닫기 메시지는 NEXUS 업무 앱 닫기와 구분
- Export Center·History Viewer·Item Manager·ORDER Q 복귀 근거는 기존 검증된 `returnApp`·`returnTo`를 유지

## 9. 부모·자식 메시지 계약

메시지 schema는 `nexus-workspace-message/v1`로 고정한다.

| type | 방향 | 목적 |
|---|---|---|
| `NEXUS_WORKSPACE_HOST_READY_V1` | 부모→자식 | 부모·현재 테마·transition 식별 전달 |
| `NEXUS_WORKSPACE_APP_READY_V1` | 자식→부모 | UI 표시 준비 완료 |
| `NEXUS_WORKSPACE_NAVIGATE_V1` | 자식→부모 | 허용된 앱·route 이동 요청 |
| `NEXUS_WORKSPACE_ROUTE_CHANGED_V1` | 자식→부모 | `replaceState` 등 현재 route 변경 알림 |
| `NEXUS_WORKSPACE_BEFORE_LEAVE_V1` | 부모→자식 | 전환 전 편집 반영·저장 flush 요청 |
| `NEXUS_WORKSPACE_LEAVE_RESULT_V1` | 자식→부모 | `READY`, `BLOCKED`, `ERROR` 결과 |
| `NEXUS_WORKSPACE_THEME_V1` | 부모→자식 | 기존 테마 컨트롤러 적용 |
| `NEXUS_WORKSPACE_PRINT_V1` | 부모→자식 | 부모 포커스 상태의 Ctrl+P를 현재 앱 출력으로 위임 |

공통 envelope 예시는 다음과 같다.

```js
{
  schemaVersion: "nexus-workspace-message/v1",
  type: "NEXUS_WORKSPACE_BEFORE_LEAVE_V1",
  transitionId: "uuid",
  appId: "orderops",
  route: "orderops/list.html?orderId=..."
}
```

검증 규칙:

- 정확한 `event.origin`
- 현재 iframe의 `contentWindow`
- 등록된 `appId`와 허용 route
- 현재 `transitionId`
- 알려진 `schemaVersion`과 type

이전 frame의 늦은 메시지, 다른 창, 중첩 설정 iframe과 알 수 없는 type은 무시한다. `postMessage`에 업무 row, 주문 payload, 토큰, Repository 결과 전체를 넣지 않는다.

## 10. 이탈·저장 계약

### 10.1 공통 흐름

```text
앱 선택
→ 현재 앱 beforeLeave 요청
→ 현재 편집 DOM 값을 앱 state에 반영
→ 앱 소유 임시저장 flush
→ 실제 성공·차단·실패 응답
→ READY일 때만 iframe 탐색
→ 새 앱 UI 준비
→ 활성 탭·부모 URL 확정
```

- 변경이 없으면 즉시 `READY`를 반환한다.
- 이동을 이유로 공식 확정·Cloud 동기화·출고확정을 실행하지 않는다.
- 시간 초과를 저장 성공으로 처리하지 않는다.
- 실패 시 iframe을 제거하지 않고 현재 앱에서 원인을 표시한다.
- 빠른 연속 앱 선택은 transition ID로 직렬화하고 최종 선택 하나만 실행한다.
- 부모는 앱의 진행 중 작업을 직접 취소하거나 병렬 저장을 시작하지 않는다. 자식 앱이 단일 operation queue에서 `진행 중 공식 처리 → 최신 임시저장 → 이탈` 순서를 확정해 응답한다.
- 이미 Cloud 저장·출고확정·복구·출고결과 쓰기가 진행 중이면 결과를 확인하기 전 iframe과 부모 route를 교체하지 않는다. 성공 뒤 최신 화면 state를 다시 판정하고, 실패·충돌·사용자 확인 필요 상태면 현재 앱을 유지한다.

### 10.2 스마트입력

- `saveDraftNow()`의 호환 저장 반환만으로 완료 처리하지 않는다.
- 활성 입력을 state에 반영하고 기존 DB 자동저장 queue가 실제 성공 또는 실패로 끝날 때까지 앱 소유 lifecycle이 기다린다.
- 오류를 삼킨 queue 완료를 성공으로 변환하지 않는다.
- 저장 실패 시 현재 화면과 입력을 유지하고 `ERROR` 또는 사용자 선택이 필요한 `BLOCKED`를 반환한다.

### 10.3 출고관리

- 앱 전환 요청을 받으면 새 공식 저장·출고확정 조작의 중복 실행을 잠그고 마지막 input/change 값을 workspace에 반영한다.
- 아직 시작하지 않은 180ms 예약 timer를 취소하되 dirty revision은 지우지 않는다.
- 이미 실행 중인 임시저장 promise가 있으면 같은 저장 queue에서 그 결과를 먼저 기다린다. 기다리는 동안 입력 revision이 증가했으면 이전 성공을 최신 성공으로 간주하지 않는다.
- 진행 중 저장 뒤 최신 revision을 기존 저장 함수로 한 번 더 즉시 저장하고 IndexedDB 기록·SHA-256 검산까지 완료한다.
- Cloud 완료본 저장이나 출고확정이 진행 중이면 성공·실패·충돌 결과와 관련 상태 투영이 끝날 때까지 `READY`를 반환하지 않는다. 전환 요청이 공식 처리를 새로 실행해서는 안 된다.
- 진행 중 공식 처리가 성공했더라도 그 뒤 발생한 최신 로컬 입력이 있으면 위 임시저장·검산을 다시 마쳐야 이동한다.
- ORDER Q snapshot, source fingerprint, 직원 적요·담당 변경·패널 상태를 기존 복구 계약대로 유지한다.
- 저장 실패를 `READY`로 바꾸지 않으며 현재 패널·필터·선택·스크롤을 보존한다.

### 10.4 다른 앱

각 앱은 기존 dirty 판정과 저장 경계를 사용한다. 영구 초안 기능이 없는 앱은 다음 중 하나를 명시한다.

- 변경 없음: 즉시 이동
- 안전한 기존 임시저장 성공: 이동
- 미저장 변경 존재: 유지·이동 취소 또는 명시적 폐기 선택

부모가 앱 DOM을 추측해 업무 저장소에 직접 쓰지 않는다.

## 11. 테마·포커스·키보드·출력

### 11.1 테마

- 부모 테마를 첫 자식 준비 시와 변경 시 `ONEAPP_NEXUS_UI_THEME.apply()`에 전달한다.
- 자식은 기존 `nexus-ui:theme-change`를 발생시킨다.
- 저장·메시지 반사로 무한 반복하지 않는다.
- 글로벌헤더·앱헤더는 본문 테마와 무관하게 기존 다크 스타일을 유지한다.

### 11.2 포커스와 키보드

- 앱 준비 뒤 해당 앱의 기존 초기 포커스 또는 업무 영역으로 포커스를 이동한다.
- F2~F10 등 앱 단축키는 자식 앱에서 한 번만 실행한다.
- 부모는 앱 F키를 복제 전송하지 않는다.
- 글로벌 탭 키보드 조작과 자식 셀 편집을 분리한다.
- 이탈 취소·모달 닫기 뒤 원래 포커스를 복원한다.

### 11.3 인쇄·다운로드

- 앱의 인쇄 버튼은 자식의 기존 인쇄 함수를 실행한다.
- 자식에 포커스가 있으면 Ctrl+P가 기존 앱 인쇄 범위를 사용한다.
- 글로벌헤더에 포커스가 있을 때의 Ctrl+P는 현재 자식에 `NEXUS_WORKSPACE_PRINT_V1`을 한 번 보내고 부모 전체 문서를 인쇄하지 않는다.
- 글로벌헤더·호스트 로딩·오류 UI는 앱 인쇄에 포함하지 않는다.
- DataOps 새 창 인쇄, Excel 다운로드, 파일 드롭·선택과 팝업은 기존 동작을 유지한다.
- 물리 프린터 검수는 기술검증과 구분해 미검증 범위로 보고한다.

## 12. 출고관리 연결 보호 기준

순차 통합 단계에서 `orderops/list.html`에는 다음 연결만 허용한다.

- 임베드 조기 판정과 글로벌헤더 offset 제거
- 부모 route 알림과 검증된 내부 이동
- beforeLeave 저장 flush adapter
- 부모 테마 적용
- 현재 앱 인쇄 위임
- UI ready 신호

다음 부분은 통합 담당이 다시 구현하거나 교체하지 않는다.

- 중앙 기본표 열 key와 가시성
- 좌측 담당 변경·창고·담당·지역 필터와 창고 원본 열 선택
- 담당자별 건수
- 재고 단독 동적 열
- 단위 비교·잔량·구매필요
- 출고분석·부분출고·대체·보류·취소·충돌
- 로컬 복구 record와 Cloud plan payload
- 좌우 폭·우측 재열기·중앙 스크롤

창고 열 충돌은 기존 별칭 등록만으로 해결된 것으로 처리하지 않는다. 트랙 A가 다음 선택 계약을 구현하고, 순차 통합은 그 상태를 그대로 보존한다.

1. `창고`와 `창고코드` 등 둘 이상의 후보를 감지하면 각 열의 원본 header, 비어 있지 않은 값 수, 고유값 예시와 충돌 행의 두 값을 나란히 표시한다.
2. 관리자가 `이번 주문 파일의 창고로 사용할 열`을 하나 선택해야 재검증할 수 있다. 임의 첫 열, 열 순서 또는 별칭 우선순위로 자동 통과시키지 않는다.
3. 선택 뒤 원본 source matrix를 다시 파싱하고 창고 필터·담당 건수·주문 건수·오류 건수를 재검증한다. 성공 전에는 분석·완료 상태로 표시하지 않는다.
4. 선택값은 현재 workspace와 기존 복구 record에 source header signature·주문 import 종류와 함께 보존한다. 관리자가 기존 매핑 저장을 명시한 경우에만 같은 signature의 이후 파일에 재사용한다.
5. 다른 header signature, 다른 import 종류 또는 후보 열 구성이 바뀐 파일에는 이전 선택을 자동 적용하지 않는다. 원본 파일·두 열 값·source fingerprint는 변경하지 않는다.
6. 선택을 바꾸면 기존 파생 분석본을 `재분석 필요`로 만들되 공식 완료본·출고결과를 자동 덮어쓰거나 삭제하지 않는다.

### 14.4 높이·반응형

- 1920×1080 / 100%
- 1366×768 / 100%
- 1280×720 / 100%
- 1024×768 / 125% 상당 CSS 폭
- 지원 모바일 폭 390px

전환 전후 글로벌헤더와 iframe 시작점 차이는 1 CSS px 이내다. 전체 화면 흰색 번쩍임, 헤더 공백, 이중 높이 차감, 페이지 전체 가로 overflow가 없어야 한다.

- 1100px 이상: 3개 섹션 같은 행과 좌우 독립 resize

- 639px 이하: 좌측 상단+중앙 하단, 우측 overlay 재열기
- 각 breakpoint 왕복 뒤 데스크톱 저장 폭, 우측 열림 상태, 필터·입력·선택·스크롤 보존

## 15. 배포와 운영 전환

각 PR은 병합과 Pages 배포 성공을 구분해 확인한다.

1. PR A와 PR B는 준비된 순서로 각각 병합·배포하며, A는 독립 출고관리 운영검증, B는 통합 URL 비기본 진입 검증
2. A·B 양쪽 배포와 독립 검증이 모두 성공했는지 병합 게이트 확인
3. PR C 배포 후 통합 URL의 7개 앱·42개 전환 검증
4. PR D 배포 후 홈 기본 진입과 직접 URL fallback 검증

운영 검증은 읽기 전용 실제 자료와 격리 합성자료를 구분한다. 실제 고객 출고확정·마스터 변경·Cloud 공식 저장·전표 확정을 기술검증에 섞지 않는다.

각 단계에서 다음을 기록한다.

- PR URL
- 개발 commit
- 병합 commit
- Pages run과 conclusion
- 운영 파일 version·hash·병합 SHA 일치
- 직접 실행한 브라우저·화면 크기·시나리오
- 미검증과 남은 위험
