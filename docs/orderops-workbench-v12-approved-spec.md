### v1.2 보완 범위

v1.1에서 명세 수준으로 통과한 출고 재개 조건·작업값 보존·PM 검증 절차는 유지한다. 이번 변경은 **발주현황과 실제 F10 구매업로드의 대상·수량 연결**, 그리고 **명세 검토자/사용자 역할 구분**이다. 전체 기능 재검증을 다시 수행한 것은 아니다.

- F10의 양식·시트 구성은 유지하되, 구매업로드의 대상 행·수량을 현재 창고재고 판단과 연결하는 최소 수정을 개발 범위에 포함한다. §5.3·10.2·11·U06-d·U26의 모순된 수량 불변 조건을 함께 정정한다.
- 명세 검증은 **기획자(이번 재검증 의견 작성자)**, 최종 실무 확인은 **사용자**가 담당한다. Codex PM과 개발자의 역할·검증/배포 순서는 유지한다.

## 1. 목적과 적용 우선순위

기존 오더리스트의 정보와 조작을 유지하고, 좌측은 파일 준비, 우측은 조회·수정, 중앙 하단은 저장·자료 불러오기·출고·출력을 담당하도록 재배치한다. 중앙 작업 화면은 기존 주문현황을 기본으로 한다.

이번 기획을 적용하면서 다음 과거 OrderOps UI 규칙을 대체한다. 다른 앱에는 적용하지 않는다.

| 기존 규칙 | 본 명세의 적용 규칙 |
|---|---|
| 좌측 주문 요약 상시 표시·닫기 금지 | 좌측 파일 준비 패널, 사용자가 닫기·다시 열기 가능 |
| 중앙 기본 분석 4→6열 및 별도 주문 상세 | 기존 `allocations` 주문현황 한 화면, 분석 전에도 같은 열 체계 |
| 우측 결과·다음 단계 또는 빈 보조 공간 | 중앙 선택에 연결된 조회·작업본 수정 |
| 앱헤더 파일 업로더 중심 | 여섯 현황 전환·실행·초기화 중심 |
| 상시 별도 출고 입력표 | 조건부 실제출고 열과 하단에서 여는 출고 확인 영역 |

데이터 소유권, 기존 계산 의미, 저장·복구·출고 원장 계약은 계속 적용한다. F10은 양식·시트 구성을 보존하되, 구매업로드 대상·수량의 오래된 계산값 연결은 §5.3에 따라 수정한다. 과거 HTML 파일을 통째로 복원하지 않는다.

### 1.1 포함·제외

포함: 앱헤더 내부 재배치, 좌·중·우 동일 부모 구성, 기존 주문현황 복원, 파일별 준비·매핑·일괄 적용, 우측 조회·작업본 수정, 발주현황 조회·F10 구매 대상/수량 연결 보정, 중앙 하단 작업바, 기존 출고 기능 연결, 반응형·접근성·상태 보존, 회귀검증·배포 검증.

제외: 공통 NEXUS 헤더·앱 이동 순서 변경, `smartinput/*` 및 `orderops_list.html` 수정, ORDER Q 원장·거래처 마스터 직접 수정, 자동 판매등록·ERP 반영, 신규 재고 차감 정책, 새로운 필수 업로드 종류, 새 범용 계산 엔진, DB 이전·초기화. 스마트입력 견적서 성능 개선은 별도 작업이다.

## 2. 소스 대조 결과와 구현 분류

| 항목 | 기준 소스의 현재 상태 | 구현 분류 |
|---|---|---|
| 주문현황 열·편집 | `getPreviewDefinitions()`에 `allocations`가 존재. 기본값은 `readiness` 우선이며 실행 후에도 `readiness` 선택 | 유지 + 기본 진입 변경 |
| 좌·중·우 구조·하단바 | `normalizeOrderOpsWorkspaceDom()`이 기존 DOM을 이동해 생성 | 재배치·중복 생성 정리 |
| 파일 매핑 | 파일/시트/열 별칭 설정과 창고 중복 열 선택은 있음. 임의 파일별 시트·헤더행·데이터 시작행·모든 열 위치 매핑 UI는 없음 | 신규 준비 UI + 파서 입력 옵션의 제한적 확장 |
| 발주현황 | 독립 preview ID 없음. `buildPurchaseManagementSheet()`는 정의되어 있으나 현재 F10 `buildWorkbook()`에서 호출하지 않음 | 현재 `getInventoryViewRows()`와 구매업로드 판정에 연결하는 새 조회 화면 |
| 실제 F10 구매업로드 | `getPurchaseUploadRows()`가 `purchaseManagement`의 이전 대상/수량을 읽고 `buildPurchaseUploadSheet()`가 그대로 출력. 출력 후 안내는 별도 엔진 선정 결과를 사용하여 서로 다를 수 있음 | 양식·시트 구성은 유지하고 구매 대상·수량·안내 건수 연결을 동일 기준으로 최소 수정 |
| 우측 상세 | `renderInventoryInspector()`는 현재 안내 문구를 표시하고 상세 영역을 비움 | 새 상세 UI. 기존 조회·수정 함수를 연결 |
| 담당자 변경 | `setCustomerManager()`가 안정 거래처 키 전체 또는 주문·창고 범위에 적용 | 우측으로 이동·영향 범위 표시 |
| 실제출고 | 중앙 조건부 실제출고 열, 별도 실행표, `state.shipmentDraft`, 기존 명령·결과 저장소 존재 | 단일 초안으로 연결·상시 중복 표 제거 |
| 출고 문서 창고·담당 | `shipment-result-core.js`가 원본 Snapshot의 창고·담당을 기록 | 작업본 차이 검사 필요. 원본 수정 기능으로 과장 금지 |
| F8 | `buildCloudEnvelope()`가 유효한 `planId`·단일 기준일을 검사 | 기존 Cloud 완료본 저장 유지. 모든 자료에 가능한 저장으로 표시 금지 |

특히 `TOTAL_ONLY`는 기준 소스에서 `planId`가 없어 F8 경로의 조건을 충족하지 못한다. 비교 작업의 로컬 복구와 F8 Cloud 저장을 구분한다. 이 UI 개편으로 총량 재고 Cloud 저장 지원까지 완료했다고 보고하지 않는다. 해당 지원이 별도로 변경·병합되면 최신 main의 기능을 보존하고 이 표와 인수시험을 갱신한다.

## 3. 화면 구조와 공통 동작

```text
NEXUS 공통헤더 — 변경 없음
출고관리 앱헤더 — 현황 6개 / 실행 / 초기화 / 기존 환경설정
작업영역: 동일 부모
├─ 좌측 파일 준비 패널 [닫기 / 다시 열기]
├─ 중앙 작업 패널
│  ├─ 검색·필터·정렬·열 설정·프리셋
│  ├─ 현재 현황 표 [가로·세로 스크롤]
│  └─ 작업바 [저장·상태] … [자료 불러오기·출고·인쇄·Excel·기타]
└─ 우측 조회·수정 패널 [닫기 / 다시 열기]
```

1. 좌·중·우는 작업영역의 직접 자식이다. 좌우 패널을 중앙 결과 카드 안에 넣지 않는다. 조절 손잡이·접근성 보조 노드는 업무 패널로 세지 않는다.
2. 중앙은 `min-width: 0; min-height: 0`인 세로 flex, 표 영역은 `flex: 1; overflow: auto`, 작업바는 `flex: 0 0 auto`로 구성한다.
3. 하단바는 중앙 패널의 자식이며 표 스크롤 영역과 형제이다. 전역 fixed footer로 만들지 않는다.
4. 화면의 외곽 가로 넘침 없이 표·앱헤더 제어군·하단바 내부에서 각각 가로 접근을 제공한다. 마지막 행과 가로 스크롤바를 작업바가 가리지 않는다.
5. 기존 다크 앱헤더 56px·앱 명칭 시작선을 유지한다. 메뉴/선택 팝업은 `document.body` 또는 지원되는 top layer에 두어 헤더·작업바의 overflow에 잘리지 않게 한다.
6. 정적 DOM과 런타임 재배치 중 한 생성 경로만 유지한다. 초기화 함수를 반복 호출해도 중복 ID·버튼·이벤트·작업바가 생기지 않아야 한다.

### 3.1 반응형과 패널 상태

폭 구간은 독립 실행에서는 현재 뷰포트, 통합 실행에서는 iframe의 CSS 뷰포트를 기준으로 한다. 실제 패널 너비 상한은 작업영역의 가용 폭으로 다시 제한한다.

| 폭 | 좌측 | 중앙 | 우측 | 폭 조절 |
|---|---|---|---|---|
| 1100px 이상 | 열림 상태일 때 같은 행 | 남는 폭 우선 사용 | 열림 상태일 때 같은 행 | 좌우 독립 조절 |
| 640~1099px | 같은 행, 사용자가 닫기 가능 | 가용 폭으로 축소·표 내부 가로 스크롤 | 오른쪽 overlay | 좌측 및 우측 overlay 모두 조절 가능 |
| 639px 이하 | 왼쪽 overlay | 기본적으로 전체 가용 폭 | 오른쪽 overlay | 손잡이 비활성·포커스 대상에서 제외 |

- 초기 폭은 기존 OrderOps 설정을 재사용한다: 좌 380px(220~520), 우 280px(180~420), 중앙 계산 기준 최소 320px. 창 크기에 따라 실제 표시 폭만 제한하고 저장된 데스크톱 폭은 덮어쓰지 않는다.
- 640~1099px의 좌측 상한은 `작업영역 폭 - 중앙 320px - 실제 간격`으로, 우측 overlay 상한은 `작업영역 폭 - 좌우 여유 16px`와 기존 최대 폭 중 작은 값으로 제한한다. 추가 화면 축소로 인라인 배치가 불가능하면 보조 패널을 overlay로 전환한다.
- 639px 이하에서는 좌우 중 한 overlay를 표시한다. 사용자가 다른 패널 열기를 선택하면 명시적 패널 전환으로 처리하고, 기존 패널의 입력·선택은 보존한다. 새로 그리기만으로 열린 패널을 닫지 않는다.
- 좌측이 닫히면 폭·간격·손잡이를 모두 제거하여 중앙에 공간을 반환한다. 공통 레이아웃 계산도 닫힌 좌측을 0폭으로 취급해야 한다.
- 새 작업에서 저장된 선택이 없으면 좌측 열림, 우측 닫힘을 기본으로 한다. 이후 사용자의 명시적 열림 상태를 우선한다. 파일 적용·실행·저장·우측 데이터 갱신으로 자동 닫지 않는다.
- 기존 우측 열림 키와 `nexus:workbench-layout:orderops:v2` 폭 설정을 호환 유지한다. 좌측 열림은 OrderOps 전용 UI 설정으로 추가한다. 업무 복구본·Cloud payload에 패널 폭을 넣지 않는다.
- 작은 화면에서 폭을 직접 조절한 값은 좁은 화면용 설정으로 보관하고 데스크톱 선호 폭과 분리한다. 다른 앱의 동일 키 형식을 일괄 변경하지 않는다.
- overlay는 열기 버튼·Escape·닫기로 조작한다. 포커스는 열린 패널 내부로 이동하고 닫으면 호출 버튼으로 복귀한다. 배경을 가리는 모달형 overlay에는 배경 입력 방지와 포커스 순환을 적용한다.

## 4. 앱헤더와 현황 전환

표시 순서: **주문현황 → 창고재고 → 발주현황 → 구매현황 → 판매현황 → 수불현황 → 실행 → 초기화**. 기존 환경설정 진입은 우측 끝의 보조 동작으로 유지한다.

| 표시명 | 내부 연결 | 데이터와 조건 |
|---|---|---|
| 주문현황 | `allocations` | 원본 주문과 기존 계산 결과. 분석 전에도 같은 표 열 체계 |
| 창고재고 | `inventory` | 기존 재고 원본/계산 조회. 자료 상태·단위 제한 유지 |
| 발주현황 | 신규 `procurement` | 현재 창고재고의 전체 재고·주문·잔량 및 구매 필요량, 구매업로드 포함/제외 판정 (§5.3) |
| 구매현황 | `purchases` | 적용된 구매 참고자료 |
| 판매현황 | `sales` | 적용된 판매 참고자료 |
| 수불현황 | `ledger` | 기존 수불 계산 결과. 별도 필수 파일 아님 |
| 실행 | `runAnalysis()` → 기존 분석 | 적용 완료 자료의 검증·계산. 공식 출고/판매/ERP 실행 없음 |
| 초기화 | 현재 작업 초기화 | §10의 범위·진행 중 작업 보호 적용 |

- 첫 진입과 실행 성공 후의 기본 탭은 주문현황이다. 자료가 없으면 같은 위치에 주문현황 열 틀과 준비 안내를 표시한다. 재고만 적용해도 자동으로 다른 현황을 기본 탭으로 바꾸지 않는다.
- 다른 현황은 사용자가 직접 선택한다. 자료 없음, 실행 전, 비교 전용, 오류를 구분해 해당 표 위치에서 안내한다. 미실행을 정상 0건으로 표시하지 않는다.
- 여섯 탭은 모두 고정 노출한다. 데이터가 없는 탭을 선택해도 파일 업로드 창을 강제로 열지 않는다.
- 검색·열별 필터·정렬·열 표시/너비·프리셋은 중앙 상단에 유지한다. 현황별 조건을 복원하고 유효한 기본 프리셋은 기존 적용 시점에만 적용한다. 단순 재렌더링으로 사용자 조건을 재설정하지 않는다.
- 검증요약·전달사항 확인·미매칭 조회 등의 기존 기능은 중앙의 관련 메뉴나 해당 현황의 하위 상태에서 접근 가능하게 한다. 새 일곱 번째 상위 탭으로 늘리거나 기능을 숨긴 채 삭제하지 않는다.

## 5. 중앙 오더리스트 보존 계약

### 5.1 기본 열과 원본 의미

기본 순서:

`창고 → 거래처 → 그룹 → 담당자 → 상품코드 → 품명 → 규격 → 합계 → 주문 → 단가 → 창고별 재고 열 → 전달사항 → 구매`

- `allocations`의 기존 안정 column key와 저장 프리셋을 재사용한다. 사용자 설정이 있으면 이를 우선하며 기본 순서는 신규/초기 설정에 적용한다.
- `합계`는 금액이 아니라 현행 주문현황의 상품코드별 주문수량 합계이다. 기준 소스의 그룹화·표시 빈도·필터 전후 의미를 비교표로 고정한다. 현재 구현은 정규화 상품코드 합계를 그 코드의 최초 원본 순회 행에 한 번 넣는다. 이를 금액합계나 창고별 잔량으로 바꾸지 않는다.
- 단위가 달라 비교할 수 없는 상품은 기존 단위 검증 결과를 표시한다. 혼합 단위를 임의 환산·합산하여 정상 수량처럼 표시하지 않는다. 기준 소스에 단위 검증과 표시 간 불일치가 발견되면 M0에서 별도 결함으로 기록하고 계산 정책을 임의 변경하지 않는다.
- 동적 창고 열은 실제 재고자료의 기존 해석·순서를 따른다. 재고가 없으면 가짜 창고 열을 만들지 않는다. 알려진 창고라도 미확인 재고는 실제 0과 구별한다.
- `전달사항` 편집은 직원 적요 `note1Original`/`note1` 경로를 유지한다. 일반 적요 `noteOriginal`/`note`는 상세/기존 선택 열에서 별도로 제공한다.
- 창고·거래처·그룹·담당자·주문수량·단가·직원 전달사항·구매의 기존 편집 가능 범위를 유지한다. 상품 식별·규격 등 읽기 전용 필드는 편집 가능으로 확대하지 않는다.
- 구매 입력의 상품코드 적용 범위, 대체/소분 처리, 대체상품 선택·실행취소·이력, 숫자 표시·색상·키보드 이동·복사를 유지한다.

### 5.2 분석 전·부분 자료·복구

- `ORDEROPS_PREVIEW`의 `workspace.allocations`를 주문현황의 같은 열 모델에 연결한다. `readiness` 전용 4~6열 표를 별도의 기본 화면으로 렌더링하지 않는다.
- 주문만 적용하면 원본 주문값을 즉시 표시한다. 주문·재고가 있어도 실행 전 결과는 `미실행`으로 구분한다. 기존 Preview가 제공하는 검증된 참고값은 참고값으로만 표시한다.
- 분석 실행 후 같은 원본 행 ID로 결과를 연결한다. 계산 실패 시 마지막 정상 작업본과 입력을 유지한다.
- 원본 시트/행 번호, ORDER Q `orderItemId`, workspace 식별자를 포함해 선택을 식별한다. 화면 행 번호·정렬 순서만으로 수정 대상을 찾지 않는다.
- 과거 복구본의 `activePreview=readiness`는 화면 진입 시 `allocations`로 해석한다. 원본 복구 레코드를 일괄 수정하지 않는다.
- 기존 `readiness` 전용 프리셋은 보존하되 열 번호로 `allocations`에 강제 적용하지 않는다. 역할이 명확히 일치하는 설정만 호환 적용하고 나머지는 미적용 이유를 표시한다. 기존 `allocations` 프리셋은 그대로 복원한다.
- 필터로 선택 행이 숨겨지면 선택 대상을 유지하고 `현재 조건에서 숨김`을 표시한다. 자료 교체로 행이 사라지면 이유를 알리고 선택을 해제한다. 임의로 첫 행을 대신 수정하지 않는다.

### 5.3 발주현황의 구체적 범위

발주현황은 **현재 창고재고 조회와 구매업로드의 부족 판단을 설명하는 화면**이다. 예전 `발주관리` 시트나 서울 창고만을 기준으로 새 구매 필요량을 계산하는 화면이 아니다.

#### 5.3.1 계산·출력 연결 기준

1. 재고·주문·잔량·구매 필요수량은 `engine.getInventoryViewRows(workspace).rows`의 동일 상품 행에서 가져온다. 표시값은 각각 `stockTotal / orderQuantity / remainingQuantity / purchaseNeed`이다. 유효한 비교 가능 행에서는 현행 엔진의 전체 유효 창고재고와 주문수량을 사용하고, 부족량은 음수 잔량의 절댓값이다. 단위 비교 불가·재고 미확인·TOTAL_ONLY 등의 제한은 그대로 유지한다.
2. `workspace.purchaseManagement[].purchaseNeed`나 `seoulRemaining`의 이전 값을 발주현황 또는 실제 구매업로드의 수량 근거로 직접 복사하지 않는다. `buildPurchaseManagementSheet()`를 다시 활성화하거나 그 필터를 새 기준으로 삼지 않는다.
3. 현재 F10은 `downloadResult() → workbookTools.downloadWorkbook() → buildWorkbook() → buildPurchaseUploadSheet() → getPurchaseUploadRows()` 경로이다. 기준 소스의 `getPurchaseUploadRows()`는 이전 `purchaseManagement.purchaseNeed`를 읽으므로, 엔진의 `getPurchaseUploadSelection()` 결과가 올바르더라도 실제 파일은 다를 수 있다. 출력 후 안내의 선정 건수만 바꾸는 것으로는 수정 완료가 아니다.
4. **최소 수정:** 실제 구매업로드 행 선정·수량 생성 경로를 동일 작업 버전의 `engine.getPurchaseUploadSelection()` 결과에 연결한다. `included`의 상품별 행과 재산정된 `purchaseNeed`를 출력에 사용하고 `excluded`의 사유를 조회에 표시한다. 별도 서울 기준 계산·워크북 전용 부족 계산을 추가하지 않는다. 기존 실행 가능 조건·단위 검증·대체/소분 및 참고행 제외 계약은 유지한다.
5. 새 발주현황, 실제 구매업로드 시트, 출력 후 안내 건수는 같은 검증된 작업 버전의 선정 결과를 사용한다. 현황 검색/필터/정렬 때문에 F10 대상이 바뀌면 안 된다. 출력 도중 입력 버전이 바뀌면 출력 기준 버전과 이후 변경 상태를 구분하고, 파일과 안내가 서로 다른 버전을 사용하지 않게 한다.
6. 연결은 `getPurchaseUploadRows()`와 이를 사용하는 통합 F10·기존 개별 구매업로드 생성 경로 모두에 적용한다. 함수명·공개 호출 계약을 가능한 한 보존하고, 기존 엔진 참조 또는 명시적 의존성 전달로 처리한다. UI 상태/DOM 전역에만 의존하는 별도 출력 경로를 만들지 않는다. 선정 결과를 구하지 못하면 오류를 알리고 이전 수량으로 조용히 fallback하지 않는다.
7. 기준 소스의 조회 helper에는 참고행 보충·통계 갱신 같은 부수효과가 있다. 새 발주 조회와 출력 선정은 동일 확정 작업 버전에 대한 파생 캐시 또는 격리 복사본에서 처리한다. 출력 전 활성 `workspace.purchaseManagement`를 새 수량으로 덮어쓰는 편법을 금지한다. 탭 열기·검색·인쇄·Excel 생성만으로 활성 원본/작업값·구매 입력·이력·복구본을 변경하지 않는다.
8. M0에서 현재 불일치를 재현하는 fixture를 고정하고, 개발 후 엔진 선정값뿐 아니라 **실제 F10의 구매업로드 시트에 기록된 상품·수량**을 대조한다. 이번에 확인된 이전 수량 연결 오류는 구현 대상이며, “기준선 결함이므로 미검증으로 남김”으로 완료 처리하지 않는다. 이 연결 보정 이외의 계산 정책/단위 정책 변경이 필요하면 별도 판단한다.

#### 5.3.2 열과 표시 대상

기본 열은 `상품코드·품목명·규격·단위·총주문·전체 창고재고·잔량·구매 필요수량·구매·업로드 판정`이다. 거래처별 주문/단가, 구매처, 일반 적요와 직원 전달사항, 창고별 내역은 선택 열·상세로 제공한다. 두 적요 원문은 별도 필드로 유지하며, 합쳐진 표시문을 원문으로 저장하지 않는다.

- 기본 목록은 비교 가능한 행 중 구매 필요수량이 양수인 품목이다. 대체·소분은 부족 여부와 별개로 기존 업로드 제외 이유를 표시한다. 부족 없음·미확인 항목은 상태별 조회에서 확인할 수 있게 한다.
- 주문이 없는 재고 참고행·카테고리 참고행·단위 미확인·재고 없음·기준일 부족을 정상 구매 대상과 혼합하지 않는다. 기존 함수가 반환한 판정과 사유를 보존한다.
- `구매`만 기존 구매 입력 함수와 적용 범위를 재사용한다. 나머지 계산값은 읽기 전용이다. 입력 변경 후 현황과 업로드 판정은 같은 작업 버전으로 갱신한다.
- 실행 전에는 미실행, 제한 자료는 제한 사유를 표시한다. `null`·미확인을 0으로 바꾸거나 TOTAL_ONLY에서 새 구매 제안을 만들지 않는다.

#### 5.3.3 고정 계산 사례와 검증 정정

다음은 단위 EA 일치·유효한 주문/재고·기존 출력 가능 조건이며, 이전 `purchaseManagement.purchaseNeed=10`이 남은 경우를 포함하는 합성 재현 기준이다.

| 주문 | 주문 지정 창고 재고 | 다른 창고 재고 | 현재 창고재고 잔량 | 수정 후 구매 필요 | 현재 F10 재현값 | 수정 후 실제 구매업로드 |
|---:|---:|---:|---:|---:|---:|---|
| 10 | 0 | 20 | +10 | 0 | 10 | 해당 상품행 제외 |
| 10 | 0 | 4 | -6 | 6 | 10 | 제외 조건이 없으면 수량 6 |

`현재 F10 재현값`은 기획자가 출력행 생성 함수를 직접 실행해 제시한 결과이며, PM은 이번에 실제 출력의 이전 수량 참조와 안내 건수의 별도 엔진 참조를 소스로 재대조했다. 브라우저 다운로드·운영 출력까지 이번에 재검증한 것은 아니다.

v1.1에서 사용한 제한적인 합성 fixture의 통과 결과는 위 불일치 조건까지 검증한 증거가 아니었다. 따라서 “기존 F10 수량 불변” 인수조건을 정정하며, 이 표의 수정 후 값은 **아직 구현되지 않은 목표값**이다. 이전 수량이 10으로 남아 있어도 실제 구매업로드는 각각 제외/6이어야 한다.

F10의 시트 존재 조건·시트명·순서·열 이름/순서·서식·숫자/텍스트 형식과 구매업로드의 대상/수량 이외 필드 매핑은 유지한다. **구매업로드 대상 행과 수량은 위 연결 보정에 따라 변경될 수 있으며, 제외에 따른 데이터 행 수/출력 범위 변경은 허용한다.** 다른 시트의 계산·원문·수량·판매업로드는 변경하지 않는다. 새 화면의 F9는 현재 표시 조건을 인쇄한다.

## 6. 좌측 파일 준비와 적용

### 6.1 화면 구성

패널 상단 `Excel 파일 / 지우기 / 적용`, 파일명 목록, 선택 파일의 자료 유형·시트·헤더행·데이터 시작행·원본 미리보기·열 매핑 순서로 구성한다. 같은 패널 안에서 파일을 전환하며 단계형 마법사나 파일별 별도 페이지는 만들지 않는다.

- 지원 유형은 현행 `orders / inventory / purchases / sales` 네 가지이다. 발주·수불은 신규 업로드 유형으로 추가하지 않는다.
- 한 통합 Excel의 여러 시트는 동일 파일 하위의 준비 항목으로 관리할 수 있다. 한 시트가 여러 종류로 해석되면 명시적으로 하나를 선택한다.
- 여러 파일을 준비할 수 있지만 한 번의 적용에서 종류별 활성 자료는 하나이다. 동일 종류 후보가 여러 개이면 사용할 후보를 선택한다. 파일들을 임의로 합치거나 마지막 파일로 덮어쓰지 않는다.
- 파일당 기존 25MiB 상한과 형식 검사·오류 처리를 유지한다. 읽은 파일은 불필요하게 반복 파싱하지 않는다.
- 자동 판별 결과는 추천 상태이다. 실제 구조·필수 필드 검증이 완료되어야 적용 가능하다. 파일명만으로 확정하지 않는다.

### 6.2 준비 상태와 매핑 계약

준비 모델은 UI 내부 상태이며 외부 API나 새 DB schema가 아니다.

| 항목 | 보존 내용 |
|---|---|
| 파일 식별 | 준비 ID, 파일명·크기·원본 SHA-256, 시트명 |
| 원본 증거 | 원시값/표시값 행렬, 원래 행·열 위치, 접근 가능한 수식·셀 형식 증거 |
| 구조 선택 | 0-based 헤더행·데이터 시작행, UI에는 Excel과 같은 1-based 행 번호 |
| 열 매핑 | 원본 열 인덱스, 원본 헤더, 업무 필드 key 또는 명시적 비매핑, 자동추천/사용자선택 출처 |
| 검증 | 필수 누락·중복·잘못된 값과 파일/시트/셀 위치, 제외행 사유 |
| 적용 상태 | `READING / PREPARED / INVALID / READY / APPLYING / APPLIED / ERROR` 및 변경 버전 |

- 데이터 시작행은 헤더행보다 뒤여야 한다. UI에서 행·열을 고르는 동안 원본 행렬을 잘라 덮어쓰지 않는다.
- 필수 필드는 엔진의 현행 목록을 사용한다. 주문은 품목코드·품목명·규격·수량·적요·적요1·거래처·그룹, 재고는 품목코드·품목명·규격·수량 및 유효한 동적 창고수량 구조, 구매는 품목코드·품목명·수량·구매처, 판매는 품목코드·품목명·수량·거래처를 검증한다.
- 동일 업무 필드에 여러 원본 열이 연결되면 후보값과 출처를 표시해 사용할 열을 고르게 한다. 기존 창고/창고코드 충돌 선택을 이 흐름에 통합한다. 비매핑은 원본 삭제를 뜻하지 않는다.
- 주문/재고 파서는 현재 헤더 자동 탐색을 사용한다. 명시 헤더행·시작행·열 위치를 전달하는 선택 옵션을 기존 파서에 추가하되, 옵션이 없으면 현행 결과가 완전히 같아야 한다. 수량·상품코드·단위 파싱이나 계산식은 바꾸지 않는다.
- 명시 매핑은 파서의 필수 필드·중복 검사에도 동일하게 적용되어야 한다. 표시 헤더만 바꾸어 검사를 우회하지 않는다. 재고 창고수량 열의 동적 역할과 원본 열 인덱스를 보존한다.
- `1,000`, 공란, 실제 0, 음수·소수, 선행 0 상품코드, 원문 적요를 기존 파서 규칙대로 보존한다. 제외행이 있으면 원행과 사유를 확인할 수 있어야 하며 정상 행 수만으로 전체 적용 성공을 판단하지 않는다.
- 기본은 현재 준비 파일에만 적용한다. 기존의 명시적 `같은 원본 열 구성에 사용` 기능만 호환 재사용하고, 이번 작업에서 새 범용 양식 저장 기능을 만들지 않는다. 구조 서명·원본 열이 다르면 기존 창고 선택값을 자동 재사용하지 않는다.

### 6.3 적용의 원자성·입력 보호

```text
준비 초안 검증
→ 이번 적용의 종류별 자료와 제거 대상 확정
→ 예약 저장 정리·진행 중 저장/출고/분석/재고 적용 결과 확인
→ 현재 편집값 수집·마지막 정상 작업 복구 저장 검증
→ 최신 작업 ID/변경 버전 기준으로 후보 구성
→ 모든 대상 검증
→ 최종 입력 변경 재확인·짧은 커밋 구간
→ 적용 확정 및 화면 교체
```

- 전체 준비 목록이 아니라 이번 적용에 포함된 후보를 검사한다. 한 대상이라도 오류면 이번 배치를 적용하지 않는다. 정상 작업본을 먼저 비우지 않는다. 사용자는 오류 후보를 적용 대상에서 제외하고 다시 적용할 수 있다.
- 원본 교체·사용해제 시 종류·영향받는 주문·편집값을 먼저 안내한다. 정상적인 신규 파일 준비나 단순 매핑 선택마다 확인창을 띄우지 않는다.
- 재고만 교체하면 주문·담당·적요·수기 입력을 유지하고 기존 재고 적용 트랜잭션을 재사용한다. 여러 종류를 함께 교체하면 그 범위를 분명히 표시한다.
- 적용 대기 중 추가 입력은 최종 후보에 포함해야 한다. 작업 ID/버전이 바뀌면 최신 작업으로 다시 후보를 만든다. 화면 교체 직전까지 동시 입력·다른 적용과 충돌하지 않게 한다.
- 후보는 적용 확정 전 복구 대상에 게시하지 않는다. 재고 적용의 기존 `STAGED → PUBLISHED`와 `inventoryApplyCommittedAt` 경계를 보존한다. 일반 파일 배치도 후보와 확정 복구본을 구분하되 재고 전용 완료 표식을 다른 종류에 임의 재사용하지 않는다. 중간 종료 시 마지막 확정 작업이 복구되어야 한다.
- `지우기`는 선택한 준비 항목을 대상으로 한다. 미적용 항목은 준비 목록에서 제거한다. 이미 적용된 항목은 사용해제 예정으로 표시하고, 영향 확인 및 `적용` 성공 시 작업 자료에서 제거한다. 취소 시 기존 작업은 그대로다.
- 적용 결과에는 원본 파일/시트/행·열 연결과 명시 매핑 정보를 기존 source descriptor의 호환 가능한 선택 필드로 보존한다. 원본 hash나 기존 fingerprint 계산 규칙을 UI 편의로 교체하지 않는다. 저장·복구 왕복에서 새 선택 필드 보존을 확인한다.
- 별칭·폭 등 전역 UI 선호와 적용된 원본 증거를 구분한다. 원본 증거는 작업 저장에 포함하고 전역 별칭 설정은 기존처럼 별도 보관한다.

### 6.4 준비 상태의 보존 범위

파일명 전환·패널 닫기·화면 크기 변경·중앙 조회는 미적용 준비 초안을 유지한다. 적용된 자료의 원본·매핑은 작업 복구와 함께 복원한다. 과거 복구본에 원본 증거가 부족하면 읽기만 제공하고 매핑 재편집에 필요한 파일을 다시 선택하도록 안내한다.

미적용 File 객체와 편집 초안의 브라우저 강제 종료 후 영구 복구는 이번 범위에 포함하지 않는다. 정상 앱 이동·새로고침·초기화에서는 미적용 변경을 알려 유지/적용/폐기 판단을 제공하며, 조용히 버리지 않는다. 이를 적용된 작업본의 자동복구 완료와 혼동하지 않는다.

## 7. 우측 조회·수정

### 7.1 조회 내용과 선택

- 패널 상단에 기존 창고·담당·지역 조회와 담당자별 건수 선택을 이동한다. 담당 건수는 상품행 수가 아닌 기존 거래처/주문/창고 배송 단위이다. 현재 창고·지역 범위에서 계산하고 담당 선택만으로 분모를 잘못 줄이지 않는다.
- 필요한 배송 목록은 기존 `거래처·수량·금액·적요` 네 열을 재사용한다. 중앙 전체 오더리스트를 우측에 복제하지 않는다.
- 행 미선택 시 조회 조건과 선택 안내, 선택 시 거래처·주문·상품·단위·창고별 재고 근거와 현재 문제를 보여준다. 재고 미등록·단위 불일치·조회 오류를 구분한다.
- 중앙 행 선택은 우측 대상만 바꾸며 닫힌 우측을 강제로 열지 않는다. 사용자가 연 뒤의 갱신은 열림 상태를 유지한다.
- 집계 현황 선택은 상품 조회로 연결한다. 원본 주문행을 하나로 식별하지 못하면 주문 필드 편집을 비활성하고 대상 주문을 선택하게 한다.

### 7.2 편집 범위와 적용

| 필드 | 대상·함수 | 보호 기준 |
|---|---|---|
| 창고 | 선택 주문 원행, 기존 `setOrderValue(..., 'warehouse', ...)` | 행별 작업본 수정만 수행. ORDER Q 공식 출고는 주문 단위 단일 창고 조건을 별도 검사 (§7.3) |
| 담당자 | 기존 `setCustomerManager(workspace, customerKey, ...)` | 안정 거래처 ID/코드가 있으면 동일 거래처 전체, 없으면 기존 주문·창고 단위 |
| 직원 전달사항/일반 적요 | 각각 기존 필드 경로 | 두 적요를 합치거나 교환하지 않음 |
| 실제출고·사유 | `state.shipmentDraft[orderItemId]` | 중앙·우측·확인 영역이 같은 초안 사용 |
| 계산 재고·잔량 | 조회 전용 | 기존에 승인된 재고 보정 기능의 별도 명시 동작 외 임의 수정 금지 |

- 적용 버튼 옆에 `거래처 / 주문 수 / 변경 행 수 / 현재 값 / 변경 값`을 표시한다. 담당자 변경을 한 행 변경으로 설명하지 않는다.
- 우측 입력은 안정 대상 key에 연결한 단일 편집 버퍼로 관리한다. 별도 workspace 사본은 만들지 않는다. 같은 필드를 중앙과 우측에서 서로 다른 최신값으로 보유하지 않도록 편집 진입·적용 시 버전을 대조한다.
- 다른 행 선택 시 미적용 입력은 대상별로 보존하고 수정 대기 표시를 제공한다. 다시 선택하면 복원한다. 명시적인 취소/초기화 전에는 버리지 않는다.
- 적용 직전 대상 원행과 변경 버전을 확인한다. 다른 경로에서 값이 바뀌었으면 양쪽 값을 보여주고 조정하게 한다. 실패 시 입력 버퍼와 기존 작업본을 유지한다.
- 적용 성공 후 중앙·관련 조회·합계·담당 건수를 갱신하되 선택·스크롤·열 조건·프리셋을 보존한다. 렌더링이 우측 미적용 입력을 기본값으로 덮어쓰지 않아야 한다.

### 7.3 공식 출고 원본과의 차이·재개 조건

기준 소스의 출고 문서는 Snapshot의 `warehouseId/code/name`, `assigneeId/name`을 저장한다. 우측 작업본 변경만으로 원본이나 기존 출고 문서가 수정된 것으로 표시하지 않는다.

#### 7.3.1 수정 적용 단위

- **작업표 창고:** 기존처럼 선택한 원행에만 적용한다. 같은 주문의 다른 행까지 몰래 확장하지 않는다. 일반 Excel의 행별 작업 의미는 유지한다.
- **공식 출고 창고:** 현재 계약은 한 주문 Snapshot/출고 문서에 창고 하나이다. ORDER Q 작업에서 일부 행만 변경해 혼합 창고가 되면 `작업본 창고 불일치 — 공식 출고 불가`를 표시한다. 첫 행의 창고를 문서 창고로 채택하거나 주문을 자동 분할하지 않는다.
- 혼합 창고를 해결하려면 사용자가 작업본 변경을 명시적으로 되돌리거나, 지원되는 ORDER Q 원본 수정 경로에서 **주문 전체의 창고**를 변경한 후 최신본을 적용한다. 후자는 아래 기출고 조건에 따라 재개 가능 여부가 달라진다. 다중 창고 출고·잔량 주문 자동 분할은 본 UI 구현에 포함하지 않는다.
- **담당자:** 작업본에서는 §7.2의 거래처/배송 단위 범위를 유지한다. 공식 원본의 담당자는 주문 단위이므로 작업본의 일괄 변경을 원본 일괄 변경으로 취급하지 않는다. 영향을 받는 주문별 원본 차이를 따로 표시하고 확인한다.
- 공식 비교는 제공되는 안정 ID·코드와 대응 표시값을 기준으로 한다. 동명이인·동명 창고를 이름만으로 동일하다고 처리하지 않는다. 대응을 확정할 수 없으면 확인 필요로 남긴다.

#### 7.3.2 기출고 상태별 처리

| 상태 | 허용되는 처리 | 출고 재개 조건 |
|---|---|---|
| 확정 출고 없음, 보류 이력만 있는 경우 포함 | 작업본 변경 유지 또는 명시 취소. 필요 시 owner 경로에서 주문 전체 원본 수정 | 최신 Snapshot 적용·§9.1 작업값 조정·대상 행의 단일 창고/담당 일치·수량 검증·원본 및 출고 이력 재조회 성공 후 재개 |
| 부분/확정 출고 있음, 원본 revision/hash는 기존 유효 확정본과 같음 | 기존 확정 문서는 그대로 보존. 원본과 다른 작업본 창고/담당은 명시적으로 조정 | `reviewRequired=false`, 작업본/원본 일치, 최신 순기출고를 차감한 잔여 수량 범위에서만 추가 출고 |
| 유효 확정 출고 있음, 원본 revision/hash가 달라짐 | 최신 작업본 조회·조정과 이력 확인은 가능하나 추가 출고 차단 | 현재 소스에는 기존 확정 이력을 보존한 채 원본 개정을 승인하여 REVIEW_REQUIRED를 해소하는 명령이 없음. `최신 주문 적용`만으로 재개하지 않음 |
| 오류로 기록된 확정 건을 관리자가 실제로 취소할 사유가 있음 | 기존 명시적 취소 명령으로 보상 이력 추가. 원본 확정 이력은 유지 | 취소 결과 확인 및 전체 이력 재조회 후 남은 유효 확정본의 일치·수량·권한을 다시 검사. 취소 클릭 자체로 자동 재개하지 않음 |

**실제로 출고한 물량을 원본 변경이나 재개 편의를 위해 취소하지 않는다.** 자동 취소·일괄 역분개·확정 문서의 revision/hash 덮어쓰기·확인 플래그만 해제하는 구현을 금지한다. 원본 값을 예전 값으로 되돌려도 새 revision이면 자동 해결된 것으로 보지 않는다.

부분출고 후 원본 변경까지 안전하게 재개하는 별도 승인 명령/정합성 계약이 필요하면 범위와 사용자 정책을 별도로 확정한다. 이번 UI에서는 해당 상태를 보존하고 `최신 작업본 적용됨 · 기존 출고 확인 필요 · 추가 출고 차단`으로 표시하는 것이 완료조건이다. 이를 “부분출고 후 원본 변경 재개 지원 완료”라고 보고하지 않는다.

#### 7.3.3 확정 경계

출고 확인창을 열 때와 명령 직전에 최신 Snapshot·출고 결과 조회가 모두 성공해야 한다. 원본 revision/hash, 유효 확정본의 `reviewRequired`, 작업본 창고·담당, 잔여 수량, §9.1 미해결 충돌을 검사한다. UI에서 버튼만 막지 않고 기존 명령 어댑터 호출 경계에서도 동일 조건을 재검사한다. 조회 오류를 빈 이력/`reviewRequired=false`로 처리해 출고를 허용하지 않는다.

진행 중 확정 명령이 있으면 결과 확인 전 원본 적용·작업 교체를 실행하지 않는다. 명령 직후 원본이 바뀐 경합은 기존 확인 필요 이력으로 남기고 추가 명령을 막는다. 감사 actor와 업무 담당자는 구분하며 우측 입력으로 권한을 바꾸지 않는다.

## 9. 실제출고 기능 연결과 데이터 계약

1. `ORDERQ_READ_MODEL`과 현재 Snapshot이 있는 작업에만 기존 실제출고 기능을 연결한다. 일반 Excel을 공식 출고 자료로 자동 승격하지 않는다.
2. 중앙의 기존 조건부 실제출고 열은 유지한다. 일반 파일의 기본 열을 늘리지 않는다.
3. 중앙 위의 두 번째 상시 출고 입력표는 제거하고 `출고확정`으로 임시 확인 영역을 연다. 이 안에서 대상·주문수량·기출고·이번 실제출고·남은 출고수량·부분 사유를 확인한다.
4. 확인 영역에는 `확정 / 보류 / 이력 / 출고 취소 / 현재 작업 유지 / 최신 주문 적용`의 기존 접근 경로를 보존한다. 취소는 이력의 해당 출고결과를 대상으로 한다.
5. 중앙·우측·확인 영역은 같은 `shipmentDraft`를 읽고 쓴다. 기존 `shipmentLineInputs()`의 DOM 수집 의존을 단일 초안 읽기로 연결한다. 닫힌 확인창의 오래된 입력이 최신 중앙 값을 덮어쓰면 안 된다.
6. 빈 실제출고 입력은 기존 명시 기본값 정책을 따른다. 재렌더링만으로 사용자가 지운 값이나 직접 입력한 0을 잔여 수량으로 다시 채우지 않는다. 부분출고 사유·초과 출고·0·음수 검증은 기존 명령 계약을 유지한다.
7. 기존 명령 ID·원본 revision/hash·권한·잔여 수량·멱등성 검증을 재사용한다. 출고 명령 진행 중 중복 확정, 초기화, 자료 교체, 앱 이동이 결과 확인을 앞서지 않도록 한다.
8. 시간 초과는 실패 확정과 다르다. 기존 영수증/결과 조회로 확정 여부를 확인하고 같은 논리 요청을 새 명령으로 중복 실행하지 않는다. 결과 확인 전 현재 초안과 대상은 유지한다.
9. 출고 성공 후 기출고·남은 출고수량·출고 이력을 다시 조회한다. 명령 성공 후 조회만 실패하면 `확정됨·조회 재시도 필요`로 구분하고 다시 확정을 유도하지 않는다.
10. 중앙 재고·잔량은 기존 계산 의미를 유지한다. 출고결과를 기록했다는 이유로 공통재고를 자동 차감하거나 계산잔량과 남은 출고수량을 혼용하지 않는다.
11. 원본 변경이 저장 후 감지되는 기존 `REVIEW_REQUIRED`와 취소의 보상 이력을 보존한다. 기존 출고결과·Revision을 삭제하거나 이전 값으로 덮어쓰지 않는다.
12. TOTAL_ONLY의 창고배정·구매제안·출고확정 제한을 UI와 명령 경계에서 유지한다. 일반 주문에 붙이는 가짜 창고를 만들지 않는다.

### 9.1 최신 주문 적용 — 작업값 병합·충돌·복구

기준 소스의 `reconcileShipmentDraft()`는 주로 `shippedQuantity/reason`만 이전한다. `loadOrderQSource()`가 작업본을 재생성하므로 대체상품·수정 단가·적요의 보존을 기존 기능이라고 가정하지 않는다. 아래는 이번 개발에서 구현·검증할 보완 계약이다.

#### 9.1.1 비교 기준과 식별

같은 주문의 **이전 적용 원본(B) / 현재 작업값(W) / 최신 원본(N)**을 필드별로 비교한다. B는 변형되지 않은 적용 당시 Snapshot, W는 활성 셀·우측 미적용 입력·출고 초안까지 반영한 최신 작업 버전이다.

- 같은 `orderId + orderItemId`를 우선 연결한다. 기존 `sourceLineKey` 대체 연결은 같은 주문 안에서 양쪽 모두 유일하고 상품·단위 등 정체성이 호환되는 경우에만 사용하고 대응 근거를 기록한다. 중복·모호·상품/단위 변경 시 자동 이전하지 않는다.
- 화면 행 번호·정렬 순서·동일 상품코드만으로 연결하지 않는다. 새 주문 ID로 다른 작업의 입력을 옮기지 않는다.
- 확정 출고의 과거 `orderItemId`와 수량을 새 행 ID로 자동 재배정하지 않는다. 작업 초안 대응과 확정 원장의 대응은 별개이다.
- W가 B와 같으면 N 채택, W만 바뀌었으면 호환성 검사 후 W 유지, W와 N이 같은 값이면 충돌 없이 채택한다. W와 N이 서로 다르게 바뀌었으면 이전/작업/최신 값을 나란히 보여주고 필드별 선택을 받는다. 공란과 0을 동일한 미입력으로 취급하지 않는다.
- 원본이 제공하지 않는 구매 판단·대체 결정 등의 작업 전용 필드는 B/N 값이 없다는 이유로 초기화하지 않는다. 연결된 원상품·단위·업무 범위의 변경 여부로 재적용 가능성을 검사한다.

#### 9.1.2 필드별 보존·재검증

| 구분 | 유지·적용 규칙 | 충돌/제한 |
|---|---|---|
| 실제출고 수량·부분 사유 | 명시 입력값, 0, 공란과 문자열 원문 유지 | 최신 출고 가능량·순기출고를 다시 읽어 검증. 초과값을 자동 축소/0 처리하지 않고 수정 필요 표시 |
| 대체상품·대체 사유·연결 이력 | 현재 actualProduct 결정, 원상품 연결, 이벤트 ID 및 대체/실행취소 이력 보존. 후보 재계산 시 기존 대체 적용 경로로 재적용 | 원상품/규격/단위/행 식별이 바뀌면 자동 재적용 보류. 재선택 또는 원상품 채택을 명시. 기존 이력 삭제·동일 이벤트 중복 추가 금지 |
| 수정 단가·작업 주문수량 | 작업 수정 여부를 B와 대조하여 유지하고 금액/배정 등 파생값 재계산 | 원본도 같은 필드를 수정하면 충돌. 작업 주문수량 선택만으로 공식 shippableQuantity나 원본 단가가 바뀐 것으로 취급하지 않음 |
| 일반 적요 | 기존 `noteOriginal/note` 편집 경로의 작업값과 원문 보존 | 최신 원본의 일반 적요와 충돌 시 별도 선택. 직원 적요와 합치지 않음 |
| 직원 전달사항 | 기존 `note1Original/note1` 편집 경로의 작업값과 원문 보존 | 최신 직원 적요와 충돌 시 별도 선택. 수정된 *Original 필드를 불변 원본 B로 오인하지 않음 |
| 창고·담당·거래처/그룹 작업 수정 | 작업 범위·변경값·관련 원행을 보존하고 대응 변화 확인 | 공식 원본에 대한 덮어쓰기 아님. 창고/담당은 §7.3을 통과해야 출고 가능하며 거래처/그룹의 원본 의미 변경도 자동 합치지 않음 |
| 구매 입력·수기 재고 보정 | 같은 상품·단위·재고 출처·창고/열 정체성이 유지되면 기존 범위대로 재적용 | 상품·단위·재고 출처/열 의미가 달라지면 미적용 후보로 보존하고 이유 표시. 다른 품목에 보정 전이 금지 |
| 기출고·잔여 출고·재고잔량·합계 | 과거 계산값 복사 금지. 최신 원본/현재 재고/확정 이력과 채택된 작업값으로 재계산 | 이력 조회 실패·단위 불일치를 0으로 보완하지 않음. 기존 확정 문서의 창고·담당·상품은 수정하지 않음 |

작업값 보존은 해당 값을 ORDER Q 원본이나 공식 출고 문서에 새로 저장한다는 뜻이 아니다. 출고 문서의 기존 필드 계약을 유지하며, 단가·적요 등의 작업 저장/복구와 공식 출고결과를 구분한다.

#### 9.1.3 추가·삭제·대상 없음

- 새 원본 행에는 최신 원본값을 넣는다. 다른 행의 대체상품·단가·적요·실제출고 초안을 복사하지 않는다. 실제출고 미입력의 기존 기본값은 적용하되 이번 확정 대상과 수량을 다시 확인한다.
- 최신 원본에서 삭제되거나 출고 대상에서 빠진 행은 새 출고 대상에서 제외한다. 이전 원본, 작업값, 대체/편집 이력, 출고 초안, 제외 이유를 `미적용 작업`으로 보관하고 복구본에 포함한다. 삭제행의 작업값은 사용자의 명시적 정리 전 자동 폐기하지 않는다.
- 삭제된 행에 기출고가 있으면 이력을 그대로 유지하고 §7.3의 확인 필요 조건을 적용한다. 다른 행에 출고량을 옮기거나 삭제행을 자동 재생성하지 않는다.
- 최신 원본에 남은 대상이 0개인 정상 응답은 `최신 출고 대상 없음`으로 표시한다. 기존 작업을 조용히 초기화하지 않고 제외 목록과 이력을 확인할 수 있게 한다. 조회 실패는 정상 0개와 구분한다.

#### 9.1.4 적용 순서와 실패 보호

1. §10의 예약 저장/진행 중 작업 순서를 따르고 B·W·현재 주문 ID·편집 버전을 수집한다. 최신 원본을 읽는 동안 입력한 값도 보호한다.
2. 최신 원본과 출고 이력을 조회하여 후보를 만들고 행 연결·필드 충돌·이력 상태·수량/단위를 검증한다. 해결되지 않은 필드 충돌은 후보 적용을 보류하고 현재 작업에서 선택할 수 있게 한다. REVIEW_REQUIRED 자체는 작업본 열람/적용을 막는 이유가 아니라 **추가 출고 차단 상태**로 유지한다.
3. 적용 직전 현재 주문 ID·편집 버전·원본 revision/hash를 재확인한다. 조회 중 W가 바뀌었으면 최신 W로 후보를 다시 만든다. 다른 주문으로 바뀌었으면 이전 요청의 결과를 적용하지 않는다.
4. 마지막 버전 확인부터 확정 게시까지 입력/저장/출고/교체를 순차 처리하는 짧은 확정 경계를 둔다. 장시간 조회 중의 입력을 막는 것으로 최신값 보존을 대체하지 않는다. 확정 중 발생한 입력 이벤트는 유실시키지 않고 적용 후 최신 작업에 순서대로 반영하거나 확정 취소 후 원래 작업에 남긴다.
5. 후보는 일반 복구 선택 대상에서 제외한다. 최신값 검증·필수 복구 저장·검산을 거쳐 적용을 확정한 본문과 확정 표식만 기존 복구 계약에 따라 원자적으로 게시한다. 아직 적용 승인되지 않은 후보를 최신 정상 복구본으로 먼저 노출하지 않는다.
6. 화면·선택·초안·필터를 일관된 작업 버전으로 교체하고 결과를 표시한다. 종료가 확정 전이면 마지막 확정 작업, 확정 후이면 새 확정 작업 전체가 복구되어야 한다. 저장 실패·충돌·사용자 취소 시 이전 화면과 최신 입력을 유지하며 부분 상태를 성공으로 표시하지 않는다.
7. 보존/추가/제외/충돌 건수, 이전·최신 원본 버전, 사용자 선택 결과를 작업 이력에 남긴다. 기존 이력은 유지한다. 대체 이력 등을 재적용할 때 기존 이벤트를 새 사용자 수정처럼 중복 기록하지 않는다.

위 metadata는 OrderOps 작업 보존 목적의 최소 확장으로 구현하고, 복구·지원되는 F8 Cloud round-trip에 포함한다. ORDER Q 원장·기존 출고결과 schema를 UI 요구 때문에 바꾸지 않는다. 현재 저장 경로가 충돌/미적용 값을 보존하지 못하면 조용히 버리지 말고 M0에 수정 범위를 기록한다.

## 10. 작업 교체·초기화·이탈과 출력

### 10.1 공통 작업 보호

예약 자동저장 정리 → 진행 중 Cloud 저장/출고/분석/재고 적용 결과 확인 → 활성 셀·우측 편집·출고 초안 수집 → 최신 작업 복구 저장·검산 → 해당 동작 순서를 따른다. 보호 대상 업무 동작만 잠그고 검색·도움말 등 관계없는 조작은 가능한 범위에서 유지한다.

- NEXUS `beforeLeave` 어댑터는 기존 `flushOrderOpsBeforeWorkspaceLeave()`와 연결한다. 파일 준비 초안·우측 미적용 입력도 이탈 판단에 포함한다.
- 실패·충돌·시간 초과 시 iframe과 경로를 먼저 바꾸지 않는다. 현재 작업과 수정값을 유지한다.
- `초기화`는 현재 준비 파일·작업 입력·분석 결과가 대상임을 설명하고 실행한다. 기존 복구본·Cloud 완료본·ORDER Q 주문·출고 이력·전역 매핑·열 설정은 삭제하지 않는다. 전용 복구 저장소 삭제 동작을 호출하지 않는다.
- 진행 중 명령이 있으면 결과 확인 후 초기화 가능 상태로 돌아온다. 자동저장 예약이 뒤늦게 초기화된 빈 작업을 정상 복구본 위에 게시하지 않도록 한다.
- 단순 저장·패널 닫기는 작업표를 비우지 않는다. 앱 이동과 다른 주문/파일로의 교체는 별도 작업 교체 경계이다.

### 10.2 인쇄·Excel

- F9는 현재 중앙 현황의 검색·필터·정렬·표시 열·열 순서를 적용해 A4 세로로 인쇄한다. 좌우 패널·작업바·팝업은 인쇄하지 않는다. 배경은 흰색이며 hover·선택·입력 포커스 배경을 제거한다.
- F10은 화면에 숨긴 행·열과 무관하게 전체 통합 workbook을 생성한다. 시트의 존재 조건·순서·열·서식·숫자/텍스트 형식은 유지한다. 구매업로드만 §5.3의 현재 선정 결과와 수량으로 연결을 보정하며, 이에 따른 대상 행·수량·데이터 범위 차이는 허용한다. 다른 시트·판매업로드 및 기존 대체/소분 등의 제외 의미는 유지한다.
- 미실행·부분 자료·TOTAL_ONLY에서는 현재 지원되는 출력 범위만 제공한다. 아직 계산하지 않은 값을 완료 결과로 출력하지 않는다.
- 인쇄 취소·다운로드 실패 후 입력·선택·스크롤·열폭·테마를 복원한다. 독립 실행과 NEXUS iframe의 인쇄 위임을 모두 검증한다.

### 13.1 성능 검증

기존 아키텍처의 터치 시각 피드백 p95 100ms 이하, 준비된 로컬 데이터 표시 p95 500ms 이하를 적용한다. 첫 파일 읽기/분석과 이미 로드한 자료의 행·현황·패널 전환을 구분한다.

같은 장비·브라우저에서 소/중/대 표본(예: 주문 100/500/2,000행, 동적 창고 3/10열)을 고정하고 기준판과 비교한다. 준비된 자료의 전환은 시나리오별 30회 이상 측정하고 DOM 변경 완료만이 아니라 다음 표시 프레임과 입력 가능 상태를 확인한다. 큰 표에서 지연이 확인되면 정의/조회 결과 재사용·변경 영역 갱신을 우선하며, 키보드·복사·필터·전체 출력 계약을 훼손하는 임의 행 생략을 하지 않는다.

이번 SmartInput 성능 진단 수치를 OrderOps의 기준 성능으로 인용하지 않는다. OrderOps 자체 측정이 필요하다.

### 13.2 관련 기존 검사

착수 시 실제 최신 검사 목록을 확인한다. 최소 관련 범위는 `test-orderops-three-section-preview.mjs`, `test-orderops-operations-improvements.mjs`, `test-orderops-dispatch-workbench.mjs`, `test-orderops-orderq-source.mjs`, `test-orderops-shipment-result.mjs`, `test-orderops-shipment-conflict-browser.mjs`, `test-orderops-common-inventory-browser.mjs`, `test-orderops-excel-cell-grid-browser.mjs`, `test-orderops-theme-browser-e2e.mjs`, 파일 분류·워크북·공통 패널·NEXUS 이동 검사이다.

PM 결과 검증은 **병합·배포 전 필수 단계**이다. 개발자가 PR을 생성하고 CI를 돌리는 것은 이 단계 이전에 가능하다. PM이 수정 요구하면 개발자가 수정·자체 테스트하고 변경된 head에 대해 PM 재검증을 받는다. 검증 후 코드나 main이 바뀌면 영향 분석·필수 검사·해당 PM 판정을 갱신한다. 승인되지 않은 head를 이전 판정으로 배포하지 않는다.

개발자·PM을 자동으로 새 작업에 배정하거나 PM이 생산 코드를 직접 고친 뒤 독립 검증으로 선언하지 않는다. 담당자나 증거가 없으면 해당 단계의 대기 사유를 보고한다. 사용자 실무 확인이 마지막 단계이므로, 이미 승인된 기술 배포를 불필요한 사전 실무 확인으로 다시 막는 구조는 아니다.

### 14.1 배포·운영 증거와 안전 경계

1. 개발자 PR/자체 보고에는 `이동 / 유지 / 정리 / 신규 구현`별 최종 변경, 보존한 계산/저장 계약, 실행 명령·환경·fixture·기대값·관찰값, 직접 검증/미검증, PR head 및 CI SHA를 기록한다.
2. PM은 기획자의 명세 검증 통과 기록, 검증한 head, 확인한 증거, 직접 실행한 범위, 남은 위험과 판정을 남긴다. 이번 문서·소스 검토를 이후 구현 결과 검증 통과로 재사용하지 않는다.
3. 개발자는 Pages 실행 SHA와 병합 SHA, 운영 HTML 및 변경 JS/CSS의 콘텐츠/hash·캐시 버전을 대조한다. 배포 실행·PR·커밋 링크를 제공한다. HEAD 요청 성공이나 Pages 성공 표시만으로 기능 정상 판정을 내리지 않는다.
4. 운영 검증은 개인 브라우저 데이터와 분리한 프로필·합성자료를 사용한다. 실제 자료는 읽기 전용으로 확인한다.
5. Cloud·공식 출고 쓰기 시험은 지원되는 격리 대상에서만 수행한다. 운영 전표를 만들어 지우거나 기존 자동저장/Revision/출고 이력을 교체하지 않는다. 격리 경계가 없으면 로컬 합성 명령 검증과 운영 읽기 검증을 구분하고 운영 쓰기 경로는 미검증으로 남긴다.
6. PM은 운영 실제 화면에서 최소 U01~U04, U06, U14~U20의 UI 연결, U22의 작업값 보존/실패 경로, U26~U32를 확인한다. 위험한 종료/취소 시험은 격리 경계에서 수행하고 환경을 명시한다. 로컬 통과를 운영 직접 통과로 옮겨 적지 않는다.
7. 중앙 기본 주문현황·분석 전 표시·패널 위치·하단바가 요구에 맞지 않거나 최신 적용에서 작업값이 유실되면 PM 통과로 판정하지 않는다. 운영에서 결함이 나오면 개발자 수정 → 자체 테스트 → PM 결과 재검증 → 재배포/기술 확인 → PM 운영 재검증으로 돌아간다.
8. 롤백 실행은 개발자 책임이며 해당 PR revert와 재배포를 기본으로 한다. PM은 대상 버전·영향·복구 결과를 확인한다. 새 UI 키/선택 metadata가 없는 이전 코드의 기존 작업 호환을 검증하며 확정 주문·Cloud Revision·출고/취소 이력을 삭제하지 않는다. 명시적 실행 승인이 없는 이번 문서 작업에서 롤백을 수행하지 않는다.

### 14.2 완료 판정과 보고

중앙 기존 주문현황과 보존 기능, 좌측 파일 준비·안전 적용, 우측 동일 작업본 연동, 중앙 내부 하단바, 단일 출고 초안, 실패·복구·원본 보호가 모두 검증되어야 한다. U06·U19·U22 하위 조건을 빠뜨린 통과 보고는 인정하지 않는다.

최종 보고에는 명세 버전·PR·head/병합 커밋·필수 CI·Pages 링크, 개발자 기술 확인, PM 개발 결과 판정, PM 운영 직접 검증, 사용자 실무 확인 상태를 나눠 기록한다. 소스 확인·격리 실행·운영 직접 검증·타 담당자 증거 검토·미검증을 구분한다.

배포 성공만으로 기능 완료라고 하지 않는다. 사용자 확인이 남으면 `PM 운영 검증 통과 / 사용자 실무 확인 대기`로 보고한다. 미검증 항목은 범위·원인·남은 위험을 명시하고 전체 운영검증/실무 완료로 표현하지 않는다. §7.3에서 제외한 이력 보존형 원본 개정 승인·재개 기능은 미구현 지원 한계로 명시하되, 이를 구현한 것처럼 완료 범위에 포함하지 않는다.
