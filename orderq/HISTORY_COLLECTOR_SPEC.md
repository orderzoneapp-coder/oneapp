# ORDER Q 기초데이터 수집·주문–판매 연결 개발명세서

- 버전: vNext 0.4.1
- 기준일: 2026-08-13
- 개발 분류: 중요 개발
- 목적: 과거 주문·판매·구매·재고·카카오 이력을 출처가 보존된 기초원장으로 수집하고, 실제 판매를 출고 증거로 연결하여 미출고 판단과 SmartParser 사전 검증 품질을 높인다.

## 1. 확정 업무 규칙

1. 주문은 수요이고 판매는 실제 출고 증거다.
2. 미출고수량은 `주문수량 - 연결된 순판매수량`이다.
3. 일반 주기는 주문일 다음 영업일 판매지만 고정 규칙으로 확정하지 않는다.
4. 판매일 당일 새벽·오전 추가 주문도 같은 출고 묶음 후보가 될 수 있다.
5. 기본 운영 마감은 12:00이며 관리자가 변경할 수 있다.
6. 주문시각이 없는 과거 Excel은 당일 추가 주문으로 자동 확정하지 않고 시간근거 부족 상태로 검수한다.
7. 부분출고, 여러 차수 출고, 여러 주문의 합산출고, 지연출고, 취소, 결품, 반품·음수판매를 보존한다.
8. 구매는 상품 확보와 입고 근거이며 주문–판매 파서 정답으로 직접 사용하지 않는다.
9. 안전재고는 이번 범위에서 계산하지 않되 후속 옵션을 위한 필드는 침범하지 않는다.
10. 이익·마진 계산은 ORDER Q 업무 의미에 포함하지 않는다. 원본 단가·합계는 미래 ERP 원장 호환을 위해 그대로 보존한다.

## 2. 운영일과 연결 후보

판매일 `S`의 후보 주문은 다음 순서로 평가한다.

1. 이전 영업일 주문
2. 판매일 `S`의 운영마감 이전 주문
3. 이전 2영업일 주문
4. 이전 3영업일 주문
5. 관리자 수동 연결 후보

주말·휴일은 영업일 달력으로 건너뛴다. 기본 마감시각, 휴일, 일자별 예외 마감은 수집기 설정으로 관리한다.

## 3. 수집 화면

- 경로: `/orderq/collector.html`
- 상단 버튼: `이력수집`
- 화면 제목: `기초데이터 수집`
- 입력: 주문현황, 판매현황, 구매현황, 재고현황, 거래처원장, 카카오/일반 텍스트
- 하나의 큰 드롭영역에 여러 파일을 놓으면 시트 구조와 열 이름을 우선하여 자동 분류한다.
- 시트명은 구조 동률 때만 사용한다. 파일명은 마지막 보조 근거다.
- 단계: 파일 분석 → 열 매핑 확인 → 오류·중복 확인 → 관리자 수집 확정 → 주문↔판매 연결 → 파서근거 후보

## 4. 출처와 원본 보존

모든 수집행은 다음 값을 가진다.

- `importBatchId`, `sourceRecordId`
- `sourceType`, `fileName`, `fileHash`, `sheetName`, `rowNo`
- `importedAt`, `importedBy`
- `rawRecord`, `normalizedRecord`
- `rowFingerprint`, `status`, `disabledAt`, `disabledReason`

같은 파일 해시는 중복 수집을 차단한다. 행 지문은 `자료종류+일자+전표+행+거래처+상품+수량+단가`를 사용한다.

## 5. 기초원장

- `businessPartners`: 고객·공급처 역할을 분리 보존
- `products`, `warehouses`
- `historicalOrderGroups`, `historicalOrderLines`
- `salesDocuments`, `salesLines`
- `purchaseDocuments`, `purchaseLines`
- `inventorySnapshots`, `inventoryLines`
- `fulfillmentLinks`
- `parserEvidence`
- `importBatches`, `sourceRecords`

판매·구매 원장은 미래 거래처별 ERP 원장의 기초자료로 재사용할 수 있도록 문서와 행을 분리한다.

## 6. 주문–판매 연결

1. 거래처와 판매일 후보 창을 먼저 만든다.
2. 주문 묶음과 판매 전표 묶음의 상품 겹침을 계산한다.
3. 같은 상품코드를 최우선으로 연결하고, 코드가 없을 때만 정규화 품명·규격·단위 근거를 사용한다.
4. 한 주문행과 여러 판매행, 여러 주문행과 한 판매행을 `allocatedQuantity`로 연결한다.
5. 음수 판매는 출고 확정이 아니라 반품·결품·취소 보정 근거로 분리한다.

연결 상태:

- `CONFIRMED`: 관리자 확정
- `STRONG`: 동일 거래처·상품코드와 높은 날짜 근거
- `PROBABLE`: 품명·규격 등 보조 근거
- `AMBIGUOUS`: 같은 점수 후보가 둘 이상
- `UNLINKED`: 연결할 판매 또는 주문 없음
- `EXCLUDED`: 취소·반품·비업무행

## 7. 파서 근거와 승격

판매 연결 1건만으로 파서사전을 확정하지 않는다.

- 1회 연결: `SALES_SUPPORTED_CANDIDATE`
- 서로 다른 주문일 3회 이상, 동일 거래처, 동일 원문표현, 동일 실제상품, 충돌 없음: `READY_FOR_ADMIN_CONFIRMATION`
- 관리자 확정: 고객 범위 `ADMIN_CONFIRMED`
- 같은 원문이 다른 상품으로 연결되면 `CONFLICT`로 전환하고 자동 적용하지 않는다.
- 출처 범위와 공통 범위 승격은 관리자 확정 없이는 수행하지 않는다.

## 8. 롤백과 감사

수집 배치 롤백은 원본을 삭제하지 않는다.

1. 배치를 비활성화한다.
2. 해당 정규화 행을 비활성화한다.
3. 해당 행만 근거인 연결을 무효화한다.
4. 파서근거와 승격상태를 다시 계산한다.
5. 다른 배치 근거가 남은 확정 매핑은 유지한다.
6. 롤백 이벤트와 수행자를 보존한다.

## 9. Cloud 2.1 안전화

- ORDER Q Push/Pull/Head는 별도 접근 토큰을 요구한다.
- 토큰은 Apps Script Property와 브라우저 로컬 설정에만 보관하고 주문·복구·동기화 payload에는 넣지 않는다.
- 주문과 주문행 저장은 사전 staging, 저장 후 재검증, 실패 시 이전 bundle 복구, 미완료 transaction 자동복구를 거친다.
- 수집 원장은 목적별 공통 시트에 증분 동기화하며 고객별 시트를 만들지 않는다.

## 10. 완료조건

1. 제공된 2026-08-10~13 판매·구매·재고 파일과 주문 파일을 구조 우선으로 분류한다.
2. 파일·행 중복을 차단하고 배치 롤백이 가능하다.
3. 전 영업일 주문과 당일 마감 전 추가 주문을 다른 시간근거로 평가한다.
4. 부분·합산·지연·음수 판매를 손실 없이 보존한다.
5. 연결 결과에서 미출고와 파서근거 후보를 확인한다.
6. 기존 수기주문, SmartParser, 중복방지, Revision 충돌 기능이 회귀하지 않는다.
7. GitHub Pages와 Apps Script 운영 배포 후 실제 URL에서 수집 화면과 Cloud 인증을 확인한다.

## 11. v0.4.1 안정화 규칙

- 과거 주문의 `rawLine`, `rawExpression`은 파싱 전 원문을 그대로 보존한다.
- 상품명이 풀리지 않은 주문은 거래처·운영일·수량·단위가 맞는 잔여 Basket 후보로만 제안하며 관리자 확정 전에는 출고로 차감하지 않는다.
- 출고량은 `양수 판매 - 반품·취소`인 순출고로 계산하고 주문별 미출고 잔량을 영속 저장한다.
- 관리자는 주문·판매 연결을 확정·변경·해제할 수 있으며 모든 조정은 재계산과 동기화 대상이다.
- 관리자 확정 파서사전은 근거 롤백·충돌 시 `REVIEW_REQUIRED`, 확정 취소 시 `INACTIVE`로 전환하며 SmartParser는 `ACTIVE` 매핑만 사용한다.
